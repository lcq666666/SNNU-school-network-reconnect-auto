## 5. 状态机转换表（实现与文档对照）

| 状态 | 进入前置 | 主要迁移 | 超时 / 失败处理 |
|---|---|---|---|
| `ETHERNET_PRIMARY` | 初始态；有线恢复 | 有线健康 → 保持（零动作）；连续可靠失败 ≥3 → `ETHERNET_SUSPECT` | 不可判定 → 不计数、不动作 |
| `ETHERNET_SUSPECT` | 连续失败达阈值 | 有线恢复 → `PRIMARY`；无线可用/需认证 → `WIFI_PREPARING`；无线不可用 → `BOTH_OFFLINE` | `suspect_timeout`(60s) 且状态不可判定 → `MANUAL_REQUIRED` |
| `WIFI_PREPARING` | 确认有线故障且无线可用 | 有线恢复 → `PRIMARY`；无线健康且切换冷却已过 → `WIFI_SWITCHING`（计划 metric_write）；需认证且认证冷却已过 → `WIFI_AUTHENTICATING`（计划 portal_post）；无线断 → 计划 wifi_reconnect（限频） | `prepare_timeout`(90s) → `BOTH_OFFLINE`；不可判定超时 → `MANUAL_REQUIRED` |
| `WIFI_AUTHENTICATING` | portal_post 已执行 | 无线健康 → `WIFI_PREPARING`；有线恢复 → `PRIMARY`（中止无线路径）；仍需认证且冷却已过 → 重试 portal_post | 尝试 ≥ `auth_max_attempts`(2) → `MANUAL_REQUIRED` |
| `WIFI_SWITCHING` | metric_write 已执行 | 出口验证 == Wi-Fi → `WIFI_BACKUP_ACTIVE`；有线恢复 → 撤销回 `PRIMARY` | `switch_timeout`(30s) 未验证 → `MANUAL_REQUIRED` |
| `WIFI_BACKUP_ACTIVE` | 切换出口验证通过 | 有线独立探测成功 → `ETHERNET_RECOVERY_CHECK`；无线不可用且有线未恢复 → `BOTH_OFFLINE` | — |
| `ETHERNET_RECOVERY_CHECK` | 有线恢复观察开始 | 稳定 ≥120s 且 ≥5 次成功且切换冷却已过 → `ETHERNET_FAILBACK`（计划 metric_write 回退）；有线再失败 → `WIFI_BACKUP_ACTIVE` | — |
| `ETHERNET_FAILBACK` | 切回 metric_write 已执行 | 出口验证 == 以太网 → `ETHERNET_PRIMARY`；有线再失败 → 撤销回 `WIFI_BACKUP_ACTIVE` | `switch_timeout`(30s) 未验证 → 撤销回 `WIFI_BACKUP_ACTIVE` |
| `BOTH_OFFLINE` | 两条路径均不可用 | 有线恢复 → `PRIMARY`；无线恢复 → `WIFI_PREPARING` | 限频 wifi_reconnect（`wifi_reconnect_cooldown` 60s） |

| `PAUSED` | `pause()`（用户暂停） | **粘性**：`resume()` → `PRIMARY` | 期间不产生任何动作 |

## 6. 只读监测模式的行为界定（重要）

`FailoverMode.MONITOR`（P3 默认）下，状态机照常运行**观测类状态**
（`ETHERNET_PRIMARY` / `ETHERNET_SUSPECT` / `WIFI_PREPARING` / `BOTH_OFFLINE` /
`MANUAL_REQUIRED` / `PAUSED`），但**不进入任何"动作已执行"的状态**：

- `EXECUTION_STATES = {WIFI_AUTHENTICATING, WIFI_SWITCHING, ETHERNET_FAILBACK}`；
- 当逻辑目标状态属于执行态时，MONITOR 保持当前状态，并在 `TickResult.predicted_state`
  报告"如果允许切换将进入哪个状态"，同时 `plan` 中仍列出**将要执行的动作**（如
  `metric_write` / `portal_post`），`executed` 恒为空、`readonly` 恒为真；
- 因此 `WIFI_BACKUP_ACTIVE` / `ETHERNET_RECOVERY_CHECK` 在真实只读运行中**不可达**
  （其前置执行态被门禁拦住）——这是"不假定成功、先证实再切换"（AGENTS §3.7）的直接结果；
- 上述 11 态的可达性由 U-3-11 以 **AUTO + 离线假执行器** 覆盖（假件零真实副作用）。

**执行器协议（P3 冻结、P5 实现）**：`executor(request) -> True|None`（成功）、`False`（失败）、
`str`（失败说明）或 `OpOutcome`；亦可为带 `execute(request)` 的对象。执行器异常被捕获并
转为失败结局（U-3-24），不让调度器崩溃。

## 7. 实施中发现并修复的缺陷

| # | 缺陷 | 影响 | 修复 | 看守用例 |
|---|---|---|---|---|
| 1 | `ETHERNET_RECOVERY_CHECK` 用 `now - (self.recovery_since or now)` 计算稳定时长 | `recovery_since == 0.0`（合法的 t=0 时刻）被 `or` 判为假值 → 稳定时长恒为 0 → **恢复判据永不满足**，有线恢复后永不切回 | 改为显式 `is not None` 判断 | U-3-10 |
| 2 | `TimerTable.note_auth` 在 P3 状态机中**无调用方** | 认证冷却从未登记 → `auth_allowed()` 恒真 → 认证可**无限重试**，`auth_max_attempts` 永不触发（违反方案 §6.3"不无限重试"） | `PORTAL_POST` 实际执行时登记 `note_auth(now, 180)`（两处：准备阶段首认证、认证阶段重试） | U-3-08、U-3-08b |
| 3 | `auth_attempts` 只在 `WIFI_AUTHENTICATING` 分支自增 | 首次认证（由 `WIFI_PREPARING` 提交）未计数 → 重试上限判定偏移 | 提交 `PORTAL_POST` 且被实际执行时统一自增 | U-3-08b |

   故障/认证/切换状态展示），并保留 P3 的单一副作用门。
5. `FailoverPolicy` 的 Metric 建议值（Ethernet=10 / Wi-Fi=50）仅为**建议**，必须结合
   实机默认路由与 RouteMetric 验证后才可使用（方案 §4.1、AGENTS §3.9）。
6. **报告命名冲突**：见文首说明；P4/P5 建议沿用 `_V0.3_` 标识，是否写入 `AGENTS.md` §2.6 待用户决定。
