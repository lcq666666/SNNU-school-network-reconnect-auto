## 1. 需求原文与语义归纳

**需求原文（用户 2026-10-16 提出，要点引录）**

- 升级目标：把当前「自动重连校园网工具」升级为**校园网双链路自动故障恢复控制器**。
- **需求 A**：任何网络「连接成功」之后，都必须进行**真实 Internet 验证**；不允许仅凭
  `Wi-Fi Connected` / `Ethernet Up` / `DHCP OK` / `Gateway OK` 判定联网。
  主验证站点 `http://www.baidu.com/`（闸门），沿用 V0.4 已验证的公网站点做交叉校验。
- **需求 B**：UU 远程（网易 GameViewer）自动恢复 —— 只有**活动链路 + 直连 Internet 验证通过 +
  恢复事件**三条件同时成立，才清退并重启用户态 UU 后台。
- **需求 C**：前端 UI 重构（网络仪表盘 / 双网卡卡片 / 恢复流水线 / 设置页 / 托盘动态菜单）。
- **需求 D**：版本 `0.4.0 → 0.5.0`，PyInstaller 重编译 + EXE 真机冒烟 + SHA256 + GitHub Release `v0.5.0`。

**语义归纳（实施口径）**

1. **Connected ≠ Internet**：网络真值 = **指定物理接口**能否通过**绕过系统代理**的**直连 HTTP**
   访问公网，而非 Windows 任务栏图标、NCSI、浏览器、Clash 或单纯 ping/DNS。
2. **验证必须绑定接口**：`verify(Ethernet) → Ethernet socket`，`verify(WiFi) → WiFi socket`；
   绝不允许「验证 Wi-Fi 时实际走了 Ethernet 默认出口」而误判 Wi-Fi 在线。
3. **验证通过才允许破坏性动作**：任何路由切换 / UU 清退的前置条件是**活动路径直连验证通过**。
4. **温备用**：Ethernet = PRIMARY，SNNU Wi-Fi = STANDBY（不主动维持认证）。
5. **不确定即不动**：任何「探测不可信」状态都必须 fail-closed，不做破坏性动作。

## 3. 总体目标与架构

```
                    CampusReconnect
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
       Network Truth   Failover       UU Recovery
         Engine        Controller       Manager
             │             │             │
       ┌─────┴─────┐       │             │
       ▼           ▼       ▼             ▼
    Ethernet     SNNU     Route       GameViewer
     Primary     WiFi     Manager     Restart
                 Standby
       │           │
       └─────┬─────┘
             ▼
    Interface-bound Internet
        (Baidu gate + cross sites)
             │
        INTERNET VERIFIED
             │
      Failover / Failback
             │
        UU Restart
             │
     NETWORK + UU ONLINE
```

**闭环行为**

- Ethernet 正常 → Ethernet PRIMARY / Wi-Fi STANDBY，两条链路**各自独立**验证。
- Ethernet 故障 → Wi-Fi 先被证实**真能上网**（必要时 Portal 认证）→ 再验证 → 确认 ONLINE →
  切 Wi-Fi 为 PRIMARY → 二次确认活动出口 → （Guard 允许时）重启 UU。
- Ethernet 恢复 → **不立即切回** → 连续稳定 → 切回 → 再次真实验证 → （必要时）重启 UU。
- Ethernet 恢复但 `verify(Ethernet) FAIL` ⇒ **即使 link=Connected 也不切回**。

## 5. 关键设计

### 5.1 PathVerificationRequest + `verify_interface_internet(path)`（V0.5-1）

新增数据结构（**优先复用** `InterfaceTransport`，不重写 socket/绑定）：

```text
PathVerificationRequest:
    role              # "ethernet" | "wifi"
    interface_index   # ifIndex
    interface_alias   # 网卡别名（展示用）
    source_ip         # 绑定的 IPv4 源地址
    gateway           # 网关（诊断用）
    ssid              # 仅 Wi-Fi；Ethernet 为 None
    network_generation# 该接口的「代」计数，用于作废旧 transport
```

新增能力：

```text
verify_interface_internet(path) ->
    verified: bool
    interface_index: int
    source_ip: str
    gate_result: <ProbeResult-like>
    cross_results: [...]
    successful_sites: [...]
    failed_sites: [...]
    elapsed: float
    reason: str          # 含 CAPTIVE_PORTAL / PROBE_UNRELIABLE 等定性
```

**硬性约束**

1. 所有 HTTP/TCP/DNS 探测**只能**经 `path.interface_index` + `path.source_ip` 出去
   （socket 级 `IP_UNICAST_IF` + `bind(source_ip)`，接口内 DNS）。
2. `requests` 会话必须 `trust_env=False`（**绕过 Clash/系统代理**）。
3. `source_ip` 变更后**旧 transport 立即作废**（`network_generation` / ip 比对），
   禁止复用旧绑定继续探测。
4. **接口约束失败** ⇒ 返回 `PROBE_UNRELIABLE`，且：
   - **不允许**触发 failover；
   - **不允许**触发 UU restart。
5. 判据沿用 V0.4：**闸门 Baidu PASS 且 交叉命中 ≥ 2**；Baidu FAIL ⇒ 直接 NOT VERIFIED。
6. Portal 劫持（重定向到门户）⇒ 定性为 `CAPTIVE_PORTAL`（不是「Internet 通」）。

### 5.2 每接口验证状态机

每个接口独立维护：

```text
DISCONNECTED → LINK_UP → IP_READY → PORTAL_REQUIRED → VERIFYING → VERIFIED
                                                              ↘ FAILED
```

UI/日志必须区分 `LINK_UP` 与 `INTERNET_VERIFIED`，禁止用单一「ONLINE」概括。

### 5.3 Recovery Event Coordinator（V0.5-2）

独立纯逻辑模块 `campus_recovery.py`。事件类型：

```text
STANDBY_CONNECTED | ACTIVE_PATH_RECOVERED | FAILOVER_COMPLETED | FAILBACK_COMPLETED
```

维护计数：`network_epoch` / `active_path` / `previous_active_path` / `verification_epoch` / `uu_restart_epoch`。

**触发规则**

| 事件 | 验证 | 路由切换 | UU 重启 |
|---|---|---|---|
| Wi-Fi standby connected | `verify(WiFi)` | ❌ | ❌ |
| Wi-Fi takeover（failover 完成） | `verify(WiFi)` → 通过 | ✅（切换已发生） | ✅（Guard+epoch 允许时） |
| Ethernet failback 完成 | `verify(Ethernet)` → 通过 | ✅ | ✅（Guard+epoch 允许时） |

**去重**：同一 `network_epoch` 只产生**一次** verification recovery、**一次** UU restart
（`tick` 重复不重复执行）。

### 5.4 UU Recovery Pipeline（V0.5-3）

建议接口：

```text
restart_after_verified_recovery(active_path, network_epoch, reason)
  1. enabled 检查（默认关闭）
  2. cooldown 检查（UU_RESTART_COOLDOWN = 300s）
  3. 本 epoch 是否已 restart
  4. 记录 UU_WAS_RUNNING（故障前是否在跑）
  5. **kill 前轻量再确认**：active path 仍可用 + Baidu 闸门仍 PASS
  6. 清退用户态 UU 进程
  7. 按自启项重新启动
  8. 等待并确认进程出现
  9. 写日志（§5.6）
 10. 失败 ⇒ UU_RESTART_FAILED，进冷却，等下一次**新的** recovery event 才允许再试
```

**安全边界（V0.5 重申）**

- 只处理已核实的用户态 `GameViewer.exe` / `GameViewerLauncher.exe`（及项目实际发现的用户态进程）；
  **不动** `GameViewerServer/Healthd/Service`，不重启 Windows 服务。
- 确认进程属于**当前用户**再结束；禁止 `taskkill /im *` 之类的宽匹配。
- `UU_WAS_RUNNING = false` ⇒ **do nothing**（不替用户把已关闭的 UU 启动起来）。
- 一次网络恢复事件最多一次 restart；避免 kill/start 连环抖动。

### 5.5 前端 UI 重构（V0.5-5）

- 技术栈沿用 Tkinter/ttk + PIL + pystray，**不引入大型 UI 框架**，保证单文件 EXE 轻量。
- 主窗口 820–920 × 560–650：顶部标题 + 右侧网络总体状态灯（Healthy/Degraded/Recovering/Offline/Unknown）。
- 双 Network Card：Ethernet（PRIMARY）/ SNNU Wi-Fi（STANDBY），显示 状态/IP/Gateway/ifIndex/SSID/Portal/Internet/最近验证。
- Recovery Pipeline 实时显示：检测 → Wi-Fi Ready → Portal → Internet Verify → Route Switch → UU Restart。
- 设置页 Notebook：基本 / 网络 / 恢复 / UU Remote / 诊断。
- 操作按钮：立即检测 / **立即验证**（分别验证 Ethernet、Wi-Fi，展示逐站结果）/ 手动重连 / **重启 UU Remote**（明确手动）。
- 托盘菜单动态刷新：主/备链路、Internet、UU 状态 + 上述操作。
- **所有网络操作继续在后台线程**；UI 只消费状态映射（`test_v05_ui_state.py` 不依赖截图）。

### 5.6 日志增强（V0.5-6）

每个 Recovery Event 记 `timestamp / network_epoch / active_path / Ethernet state / WiFi state /
Portal state / verification result / route action / UU action / final state`，形成可复盘时间线：

```text
ETHERNET_DEGRADED → WIFI_BACKUP_READY → WIFI_BAIDU_PASS → WIFI_CROSS_*_PASS
→ WIFI_INTERNET_VERIFIED → ROUTE_SWITCH → WIFI_POST_SWITCH_VERIFIED
→ UU_RESTART_STARTED → GAMEVIEWER_RESTARTED → RECOVERY_COMPLETE
```

**日志禁止出现**：密码、Portal 凭据、Cookie；账号与 MAC **脱敏**（沿用既有脱敏规则）。

## 8. 真机验收矩阵（P8 扩表，逐项单独授权）

| # | 场景 | 期望 |
|---|---|---|
| A | Ethernet 健康 + Wi-Fi standby | Ethernet PRIMARY |
| B | Wi-Fi 已连 + Ethernet 健康 | Wi-Fi verified；Ethernet 仍 PRIMARY；**UU 不重启** |
| C | Ethernet 物理断开 + Wi-Fi 已认证 | Ethernet FAIL → Wi-Fi VERIFY PASS → Wi-Fi PRIMARY → UU restart |
| D | Ethernet 断开 + Wi-Fi AUTH_REQUIRED | Wi-Fi 认证 → verify → 切路由 → UU restart |
| E | Wi-Fi Connected 但 Internet 不通 | Wi-Fi NOT VERIFIED；**不直接切换** |
| F | Wi-Fi Internet 正常但 Edge 异常 | NETWORK VERIFIED；**不**重新 Portal / 不切路由 |
| G | Wi-Fi PRIMARY + Ethernet 恢复 | 连续稳定 → Ethernet PRIMARY → 验证 → UU guard |
| H | Ethernet 反复抖动 | 无快速来回切换（滞回生效） |
| I | Portal 已认证 | 无重复认证 |
| J | 双链路皆不可用 | BOTH_OFFLINE；不无限认证 / 不无限杀 UU / 不无限改路由 |

④ Clash 系统代理 ON 下确认直连探测不经 Clash；⑤ 复现 UU「正在重新连接」卡死并验证清退重启有效。

## 11. 风险与已知取舍

| 风险 | 处置 |
|---|---|
| 接口绑定受 Windows 路由/Metric 影响仍可能走错出口 | 每次验证前核对 ifIndex/source_ip 读回；失败即 `PROBE_UNRELIABLE`，fail-closed |
| 双网卡切换瞬间探测误判 | 保留 failure threshold / recovery count / stable seconds / cooldown 滞回 |
| 认证风暴 | `auth_epoch` / `network_epoch` / `path_epoch`，一次 recovery event 最多一次认证 |
| UU 抖动重启 | 300s cooldown + same-epoch 去重 + kill 前轻量再确认 |
| 解释器层噪声（3.14.0 偶发 `STATUS_BREAKPOINT`） | 全量回归用 `gc.disable()` 可靠命令；定性为环境问题，未改产品代码 |
| UI 重构破坏网络逻辑 | UI 只在**所有功能测试通过后**开始；网络操作全程后台线程 |

## 13. V0.5 成功定义（全部满足才判 PASS）

- **网络**：Ethernet PRIMARY / Wi-Fi STANDBY。
- **探测**：Ethernet、Wi-Fi 各自独立接口受限验证。
- **假死**：程序能正确识别 `Connected ≠ Internet`。
- **Portal**：按需认证、不重复认证、不注销。
- **Failover**：Ethernet FAIL → Wi-Fi READY → Wi-Fi PRIMARY。
- **Failback**：Ethernet 稳定 → Ethernet PRIMARY（验证失败则不切回）。
- **UU**：Network Recovery → Direct Internet VERIFIED → UU Restart → GameViewer ALIVE。
- **稳定性**：无 route flapping / auth storm / UU restart storm。
- **UI**：一眼可见当前主链路、备用链路、Internet 是否真可用、Portal 状态、恢复阶段、UU 状态。
- **EXE**：Python PASS → PyInstaller PASS → EXE PASS → SHA256 PASS → GitHub Release `v0.5.0`。

**五句话总则**：① 有线优先；② Wi-Fi 温备用；③ Connected 不等于 Internet；
④ 只有真正恢复 Internet 后才重启 UU；⑤ 任何不确定状态都不做破坏性动作。
