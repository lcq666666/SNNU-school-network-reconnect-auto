# V0.11.1 活动 Wi-Fi 假死旧会话重建

## 现场故障证据与根因

本机 `CampusReconnect` 日志在 2026-11-19 20:18 至 23:57 记录了 48 次“Portal 已在线但公网探测仍未通过”。期间没有本机无线会话重建记录。当前本机配置显示独立守护和 UU 恢复已开启，但 `standby_session_reset_enabled=False`。

V0.11.0 的第二层恢复会调用 `repair_service()`。当 Portal 状态页显示本账号在线时，登录引擎会复用现有会话、不提交新认证；若随后公网验证仍失败，结果为 `AUTHENTICATED_DEGRADED`。V0.11.0 没有把这个主 Wi-Fi 结果接到会话重建器；已有重建只用于有线公网已确认时维护备用 Wi-Fi。因此控制器每次都能识别公网失败，却继续复用假死会话。UU 恢复在网络确认前不会执行，这是既有安全门，不是这次断联的起因。

## 修复内容

- 普通托盘重连和 V0.11 独立守护第二层恢复都处理 `AUTHENTICATED_DEGRADED`：只有 `auth_ok=True` 且 `network_ok=False` 才能继续。
- 只对可信快照确认的活动 SNNU Wi-Fi 操作；接口索引、源 IP、SSID 和物理无线网卡须保持一致。若系统出口指向其他接口或活动路径不明确，则停止。
- 下线前连续执行两轮 Wi-Fi 接口绑定验证。每轮必须是可信探测、闸门失败且至少两个独立交叉目标失败；探测不可靠或网络已恢复时不下线。
- 复用既有本机身份核验：Portal 在线账号、当前 IP 和同一会话记录行中的 MAC 必须完全匹配；不支持全账号注销。每 6 小时最多一次，且在下线前持久化预约。
- 登录复用 SNNU 绑定会话和 V0.11 同会话四位验证码流程。恢复结果仍须以状态页账号和公网验证为准；网络恢复后，原 UU 检查才继续。
- 保留现有 `standby_session_reset_enabled` 显式开关和默认关闭行为，不覆盖旧配置中的 `false`。设置页说明已扩大为涵盖活动 Wi-Fi 假死恢复。

## 使用边界与现场验收

- 升级后需在“设置 → 恢复”显式开启“允许断开本机校园无线会话后重新登录”。当前本机配置为关闭，因此升级不会自动启用会结束本机会话的动作。
- 真实 Portal 下线、校园网验证码和 UU 服务端连接未在本次离线验收中执行。验证码识别失败、账号被服务器再次淘汰、Portal 改版或控制端不可用时，无法由本机保证最终恢复。
- 现场验收应观察到“普通登录复用旧会话 → `AUTHENTICATED_DEGRADED` → 两轮 Wi-Fi 多目标确认 → 本机身份核验 → 单次本机下线 → 强制登录/验证码 → 公网验证 → UU 外连验证”。任何一步不确定都不得显示在线或扩大到其他设备。
