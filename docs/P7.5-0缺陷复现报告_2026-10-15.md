## 3. 逐条缺陷：源码证据与复现

### F75-01 托盘缺少真实三轴健康快照

**结论：已复现。** 生产路径下喂给 P3 状态机的快照只有 `system.online` 一个轴。

**源码证据**

- `campus_reconnect_tray.py:507` —— `self._failover_snapshot_provider = None`（全仓库仅此一处赋值，
  另两处为读取 `:596` 与测试注入）。
- `campus_reconnect_tray.py:594-603` `_build_failover_snapshot()`：provider 为 `None` 时回退
  `light_snapshot(system_online=..., system_source="托盘轻量探测")`。
- `campus_tray_failover.py:124-145` `light_snapshot()`：`ethernet` / `wifi` 两轴缺省为 `None`。

**风险**：AUTO 模式下 `NetworkFailoverManager._decide`（`campus_failover.py:586-596`）读取
`snapshot.ethernet` / `snapshot.wifi`，两轴为 `None` 即被归入 `UNKNOWN`/`UNRELIABLE`，
状态机既无法证明"以太网故障"，也无法证明"Wi-Fi 可用" —— 授权了路由切换却拿不到可依据的数据。

**复现**：`test_r75_01_...` → `AssertionError: 托盘必须接入真实三轴快照提供者（基线为 None，只有轻量探测）`

**修复方向（P7.5-1）**：托盘接入真实 `NetworkObserver` + `InterfaceHealthChecker`；
增加结果新鲜度（`generated_at` + 最大年龄）、采集超时与缓存代次检查；AUTO 数据不足时**拒绝执行**；
轻量快照仅用于显示占位，不得授权切换。

### F75-02 MONITOR / LOCKED 仍可能运行旧认证流程

**结论：已复现。** 仅监测与手动锁定下，V0.2 自动重连（含 Portal 认证、Wi-Fi 重连）仍会被触发。

**源码证据**

- `campus_reconnect_tray.py:584-592` `_failover_owns_actions()`：`return bridge.mode is FailoverMode.AUTO`
  —— **只有 AUTO** 返回真。
- `campus_reconnect_tray.py:1235-1246` `_probe_tick()`：非 AUTO 时走到
  `self._run_repair()` → `repair_once()` → `campus_core.repair_service`（Portal POST），
  随后 `self._timers.note_auth(now, self._cooldown())`。
- `campus_reconnect_tray.py:1178-1183` `_dispatch()`：`("reconnect", force)` 分支同样直接 `_run_repair()`。

**风险**：与 AGENTS §3.3「单一副作用门」冲突 —— V0.2 自动重连与 V0.3 双网卡调度并行，
存在两个副作用源；MONITOR 模式下用户以为"只读"，实际后台会提交校园网凭据。

**复现**：`test_r75_02_...[MONITOR]` / `[LOCKED]` → `AssertionError: MONITOR/LOCKED 下不得发起 V0.2 自动重连（含 Portal 认证）`

**修复方向（P7.5-1）**：统一副作用入口；MONITOR/LOCKED 下背景零认证、零 Wi-Fi 重连、零 Metric 写入；
人工手动重连保留但必须显式触发、明确确认，并与 V0.3 调度共用互斥机制与计时器。

### F75-03 非默认出口 Wi-Fi 无法可靠确认健康

**结论：已复现（两条子项）。**

**(a) 备用 Wi-Fi 永远不可证**

- `campus_network.py:520-534` `InterfaceHealthChecker.check()` 第 4 步：
  用 `route_lookup(target)`（即 `Find-NetRoute` = 系统**最佳**路由）结果比对被测接口 ifIndex。
- `campus_network.py:583-586`：出口未证实即 `state = PROBE_UNRELIABLE`。

以太网主用时，`Find-NetRoute` 恒返回以太网 ifIndex，于是 Wi-Fi 轴恒为 `PROBE_UNRELIABLE` ——
**备用链路在切换前永远无法被确认为健康**，直接卡死"先证实再切换"（AGENTS §3.7）。

**复现**：`test_r75_03_...` → `AssertionError: 以太网主用时 Wi-Fi 备用链路被误判为 PROBE_UNRELIABLE（无法证明出口）`

**(b) DNS 探测跨接口泄漏**

- `campus_network.py:373-378` `WindowsProbeEngine.dns_resolve(name)`：全局 `socket.getaddrinfo`，
  与被测接口无关；`check()` 第 7 步（`:567-574`）直接用它判 `DNS_FAILURE`。

**复现**：`test_r75_03b_...` → `AssertionError: DNS 探测必须可按接口约束（基线为全局 getaddrinfo）`

**修复方向（P7.5-2）**：分离四类能力 —— ① 系统当前默认出口识别；② 指定物理网卡的独立连通性检测；
③ SNNU Portal 请求的接口约束与**出口证据**；④ 切换完成后的实际路由与公网复核。
Windows 下接口约束采用"绑定源地址 + 校验实际本地端点（`getsockname()`）+ 路由表佐证"的可核实证据链，
不以 `source_address` 或 `trust_env=False` 声称作数。无法证明的请求一律 fail-closed。

### F75-04 Wi-Fi 重连后使用旧 IP

**结论：已复现。** 认证仍绑定 DHCP 变更前的旧源地址。

**源码证据**

- `campus_reconnect.py:889-920` `_build_composite_executor()`：构造时一次性
  `source_ip = _wifi_source_ip(report, wifi_if)`（`:901`），并由 `_portal_action()` 闭包捕获
  （`:904-911`），之后每次 `PORTAL_POST` 都用同一个 `source_ip` 调 `SnnuBackupLink`。
- `campus_snnu.py:422` `bind_source_address(self.session, self.source_ip)`：绑定的是构造期捕获值。
- `campus_snnu.py:598-637` `SnnuBackupExecutor`：`portal_action` / `wifi_action` 均为构造期注入的闭包。

**风险**：Wi-Fi 重新关联后 DHCP 常给出新地址；旧源地址绑定失败或（更糟）绑定到已失效地址，
认证请求实际走向错误接口，而"出口已确认"的证据链是基于旧 ifIndex 建立的。

**复现**：`test_r75_04_...` → `AssertionError: 认证仍绑定 DHCP 变更前的旧源地址 10.8.0.5`

**修复方向（P7.5-3）**：每次认证前重新读取接口标识、无线 IPv4、路由与最新健康状态；
为每次认证**单独建立绑定会话**（废弃旧会话与连接池）；区分"Portal 认证成功"与"公网真正恢复"；
仅在实际发生认证尝试后登记冷却；多入口并发提交凭据需互斥。继续复用 V0.2 `repair_service()`。

### F75-05 路由事务日志与回滚不够安全

**结论：已复现（三条子项）。**

**(a) 损坏日志被当作空日志**

- `campus_route_guard.py:414-429` `RouteJournal._read()`：`OSError` / `ValueError` 一律
  `return self._empty()`，不记录、不上报。

**风险**：崩溃恢复（`:747-784`）看到 `pending() is None` 即判定"无待恢复项"，
系统在未知路由状态下继续运行且被记为正常。

**复现**：`test_r75_05a_...` → `AssertionError: 日志损坏未被标记：崩溃恢复会误判为「无待恢复项」`

**(b) apply 回滚失败后清空 pending**

- `campus_route_guard.py:691-702`（写入失败）/ `:708-718`（验证未过）：
  `rollback_ok = self._restore(applied)` 后直接 `self._finish(record)`；
  `_finish`（`:796-800`）→ `journal.record_finished` 把 `pending` 置 `None` 并追加历史。

**复现**：`test_r75_05b_...` → `AssertionError: 回滚失败后必须保留恢复信息（pending/RECOVERY_REQUIRED）`

**(c) recover 回滚失败同样清空 pending**

- `campus_route_guard.py:774-784`：`rollback_ok=False` 时仍置 `status=ROLLED_BACK` 并 `_finish`。

**复现**：`test_r75_05c_...` → `AssertionError: 崩溃恢复回滚失败后不得清空 pending（否则无可靠恢复条件）`

**附加观察（未单独出用例，P7.5-4 一并处理）**

- `_write` 失败时 `record.error` 恒为 `PERMISSION_DENIED`（`:695`），未区分权限不足与其他失败。
- `verify()`（`:591-619`）只做 `Find-NetRoute` 控制面查询，**未用新鲜数据复核真实公网路径**。
- `journal._write`（`:431-441`）为直接 `write_text`，非原子写入（无临时文件 + fsync + replace）。

**修复方向（P7.5-4）**：原子化日志写入；损坏日志明确报错（`corrupted` + `last_error`）；
回滚失败保留 `pending` / `RECOVERY_REQUIRED`；切换后必须做真实公网路径复核；
切回失败必须执行实际恢复动作而非只改状态机；无可靠恢复条件时停止自动写入并告警。

### F75-06 远程敏感期判定不充分

**结论：已复现（三条子项）。**

**(a) UNKNOWN 不保守**

- `campus_remote.py:362-365`：探测失败时 `sensitive = bool(self._last_sensitive_at is not None)`；
  从未观测到敏感期时 `sensitive=False`。
- `campus_remote.py:430-437` `failback_gate()`：非敏感即返回 `True`（"无远程会话敏感期：允许切回"）。

**复现**：`test_r75_06a_...` → `AssertionError: 远控状态 UNKNOWN 必须保守推迟切回（当前：无远程会话敏感期：允许切回）`

**(b) UDP 型远控被误判空闲**

- `campus_remote.py:356-360`：只统计 `state == "Established"` 的 TCP 行；
  `udp_endpoints` 仅计数不判定；`LISTEN_STATE` 明确不参与判定。

Tailscale 以 UDP（WireGuard）承载会话，常驻监听 + UDP 端点，无 Established TCP —— 被判 `IDLE` 并放行切回。

**复现**：`test_r75_06b_...` → `AssertionError: 无法确认远控会话状态时必须保守处理（当前判为 IDLE）`

**(c) 1800s 强制切断**

- `campus_remote.py:424-427`：`deferred >= self.max_defer_seconds` 一律放行；默认值 `:313` 为 `1800.0`，硬编码。

**复现**：`test_r75_06c_...` → `AssertionError: 健康 Wi-Fi 正承载远程会话时不得为恢复有线优先强制切断（当前：远程会话已持续 3600s（≥上限 1800s）：按方案 §4.3 放行切回…）`

**修复方向（P7.5-5）**：结合具体远控软件的可验证会话信号（进程 + 已建立 TCP + UDP 端点活跃度 +
监听端口）判定；UNKNOWN 一律保守；非紧急切回优先等待会话结束；`max_defer_seconds` 改为可配置，
默认"等待空闲"策略，强制放行须显式开启并告警。

### F75-07 Windows 路由写权限

**结论：已复现（两条子项）。**

**(a) 无物理网卡允许清单**

- `campus_route_guard.py:999-1034` `WindowsMetricWriter`：只有命令白名单自检
  （`assert_write_allowed`），**无接口允许清单**，构造时不绑定角色 ifIndex。

**风险**：AUTO 授权即等于"可向任意 ifIndex 写 Metric"（含 Clash TAP、Hyper-V、WSL 等虚拟网卡）。

**复现**：`test_r75_07a_...` → `AssertionError: 越界 ifIndex 必须被允许清单拒绝（基线无任何清单）`

**(b) 权限失败后每轮重复尝试**

- `campus_route_guard.py:691-702`：写入失败分支不调用 `_note_switch()`，切换冷却未登记；
  下一轮 `switch_allowed`（`:642`）仍为真 → 每 15s 重试一次写 Metric，违反 AGENTS §3.11
  「权限缺失时提示而非反复重试」。

**复现**：`test_r75_07b_...` → `AssertionError: 权限失败后仍重复尝试写入 2 次（应只尝试 1 次并登记冷却/停止）`

**修复方向（P7.5-6）**：最小权限路由执行入口；受限执行器必须带物理网卡允许清单、参数校验、
日志与失败反馈；明确区分"未授权" / "权限不足" / "网络故障"三类结论；**不得**为方便而整体提升托盘权限。

### F75-08 看门狗与无人值守判定

**结论：已复现（三条子项）。**

**(a) 活线程卡死漏判**

- `campus_remote.py:643-644` `MonitorWatchdog.check()`：`if alive: return WatchdogDecision(action="OK", ...)`；
  心跳年龄判定（`:645-650`）只在 `alive=False` 时可达。

**复现**：`test_r75_08a_...` → `AssertionError: 活线程但心跳已停滞 500s 仍被判为 OK`

**(b) 「支持睡眠」≠「配置为睡眠」**

- `campus_remote.py:477-492` `_sleep_item()`：仅依据 `standby_available` / `hibernate_available`
  （= 系统**是否支持**），不读实际电源计划超时。

**复现**：`test_r75_08b_...` → `AssertionError: 已配置为从不自动睡眠，却仍报缺口：Standby 可用=True…`

**(c) 缺进程级独立恢复机制**

- `campus_remote.py:440-475` `readiness()`：仅 sleep / auto_logon / remote_client /
  tray_autostart / credentials / remote_reconnect 六项，无"进程整体崩溃后的独立恢复"项。
- 进程内 `MonitorWatchdog` 天然无法应对整个进程崩溃（`campus_reconnect_tray.py:774-787`
  的 supervisor 线程与主程序同进程）。

**复现**：`test_r75_08c_...` → `AssertionError: 无人值守清单缺少「进程级独立恢复机制」项（当前仅：sleep, auto_logon, …）`

**修复方向（P7.5-5）**：心跳超时优先于线程存活判定；可取消 I/O 与有限重启；重复恢复保护；
读取实际电源计划超时（`powercfg /query` 的睡眠超时值）；不默认启用 Windows AutoAdminLogon；
就绪自检新增"进程级独立恢复机制"项并明确其为人工/系统侧配置。

## 5. 遗留风险与约束（移交 P7.5-1 .. P7.5-7）

1. **复现用例当前处于 `regression` 分组**，默认集合不运行。各阶段修复后必须**转绿并移除该标记**，
   否则默认回归无法看守这些缺陷（AGENTS §2.3）。
2. **R75-03 / R75-03b / R75-04 的修复需新增能力**（接口约束出口证明、按接口 DNS、动态重绑），
   可能触及 `campus_network` / `campus_snnu` / `tests/fakes.py` 的既有契约，
   需同步评估对既有 577 项的影响（不得用永久 xfail 掩盖）。
3. **F75-07 的允许清单**会改变 `WindowsMetricWriter` 的默认行为（默认空清单 = fail-closed），
   `build_windows_route_ops` 必须显式传入角色 ifIndex，否则生产路径会被自己的门禁挡住。
4. **进程级恢复**只能在本机提示 + 配置项层面表达，无法由本程序自证；
   P8 验收时该项结论只能是 `PARTIAL` 或需用户确认。
