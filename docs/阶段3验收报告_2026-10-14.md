## 6. 与计划的偏差与说明

1. **冷却期间的探测节奏（F09）**：`watch` 在一次认证尝试后登记 `next_attempt = now + cooldown`，
   在冷却截止前**不再探测**（`wait = max(interval, next_attempt - now)`）。这是 T19/T20
   回归用例所要求的行为（3 次探测内必须出现两次间隔 ≥ cooldown 的尝试），也与「恢复不抹掉
   最短间隔」一致；冷却只禁止**新的认证**，不禁止 UI 命令、手动重连与只读诊断，冷却到期即
   恢复探测。计划文本中「冷却不禁止探测」理解为「冷却不阻塞状态机被命令唤醒」，自动探测
   节奏按保守策略放慢，避免对仍失败的链路反复尝试。
2. **`portal_login` 返回值**：为兼容既有调用（`ok, detail = portal_login(...)`）与新增分类需求，
   返回 `LoginOutcome`（`tuple` 子类，长度 2 可解包，另带 `status/error_code/already_authenticated`）；
   详细逻辑在 `portal_login_detailed`，`portal_login` 为其别名入口。
3. **`resolve_port` 兼容层**：保留 `(port, source)` 两元组签名（供既有调用与测试替换），
   失败时端口为 `None`；结构化结果由 `resolve_portal() -> PortalResolution` 提供。
4. **isp + 空运营商**：`account_to_send` 不再形成尾部 `@`（运营商为空时按 plain 提交）。
5. **`classify_network` 的落点**：用于新增的 `diagnose_network()`（`status` 命令综合判定），
   避免为分类在 `watch`/`_probe_tick` 中引入额外的真实探测。
6. **提交拆分**：计划建议 8 个提交，实际按文件职责拆为 4 个提交（core / engine / tray / tests），
   原因同阶段 2：三份源码改动互相耦合，无法在不产生不可运行中间态的前提下按 F 编号切分。
