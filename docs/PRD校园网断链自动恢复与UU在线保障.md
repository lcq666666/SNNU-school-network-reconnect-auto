# PRD：校园网断链自动恢复与 UU 在线保障

## 1. 产品目标

在 Windows 用户会话保持可用、无线网卡和校园网 Portal 可访问的前提下，校园网断链或“Wi‑Fi 已连接但无法上网”时，助手自动恢复校园网认证，并在网络恢复后保证 UU 远程用户态重新建立外部连接。

该账号实测最多允许 5 台设备并行在线；当第 6 台或更多设备登录时，校园网服务器可能挤掉旧设备。被挤设备通常仍显示 Wi‑Fi 已连接，但 Portal 会话和公网出口已失效，这种状态必须按“网络假死/认证失效”处理。目标是尽快恢复“可上网 + UU 可重连”，不能绕过服务器的设备数限制，也不能保证原有 TCP 连接完全无感。

## 2. 用户主流程

1. 助手持续检测 Wi‑Fi 关联状态、IPv4、Portal 状态和多个独立公网目标。Wi‑Fi 图标正常但交叉公网探测失败，或状态页显示本账号需要认证，均视为网络假死。
2. 检测到连续失败后，先保留已关联的 SNNU Wi‑Fi；仅在缺少地址或接口确实断开时执行 DHCP 续租或无线重连。
3. 网络路径确认后，读取本机安全凭据，向 SNNU Portal 提交：
   - 用户名/学号；
   - 密码；
   - 运营商 `mobile`（中国移动）；
   - 页面要求时的四位图形验证码。
4. 验证码图片必须和登录页使用同一会话、同一来源获取；本机 OCR 只提交格式合法的四位字符，不把验证码、密码或 Cookie 写入日志。
5. 登录后必须通过 Portal 状态页账号匹配和多目标公网验证，不能仅以“Wi‑Fi 已连接”判定成功。若 Portal 仍显示本账号在线、普通认证复用旧会话后公网仍失败，且两轮 Wi‑Fi 接口绑定探测均确认异常，可在用户开启无线会话重建后核对本机账号、IP、MAC，限定下线并强制重新登录。
6. 网络真实恢复后检查 UU：
   - 用户态 `GameViewer.exe`/`GameViewerLauncher.exe` 存在且有外部已建立连接：保持不动；
   - 用户态进程存在但外连失败：清退用户态进程，按原自启命令启动，并确认用户态进程重新出现；
   - 用户态进程完全消失但可找到 UU 自启命令：直接启动，并确认进程和外连；
   - 启动命令不存在或启动后未回来：记录明确失败原因，不误报在线。
7. 恢复过程写入时间戳日志和恢复记录，托盘状态必须显示“检测、认证、网络验证、UU 恢复”各阶段。

### 2.1 用户要求的完整闭环

一次恢复必须按下面的顺序收敛，而不是只把 Windows 的 Wi‑Fi 图标恢复为“已连接”：

1. **发现断链或假死**：连续的公网交叉探测失败，或 Portal 状态显示本账号已掉线，才进入恢复；单个探测点失败不能触发破坏性动作。
2. **恢复无线会话**：先保留已关联的 SNNU Wi‑Fi，尝试 DHCP 续租和现有会话认证。若 Portal 仍显示本账号在线但普通认证后公网仍失败，必须在活动 Wi‑Fi 上重复确认两轮可靠的多目标失败，且再次核对本机账号/IP/MAC 后，才可在明确开启的无线会话重建选项下限频下线并强制重新认证。只有接口确实断开、没有 IPv4，或同一故障周期内的有界尝试均失败时，才允许执行一次受冷却保护的 `disconnect → connect`，随后重新等待 IPv4 和 Portal。
3. **重新认证**：在同一 Portal 会话中提交保存的用户名、密码和中国移动 `mobile` 运营商参数。若页面返回四位数字图形验证码，必须从同一会话取得图片并只提交格式合法的四位 OCR 结果；图片/OCR 失败时刷新挑战并有限重试，不提交猜测值。
4. **确认网络**：登录成功还不算完成，必须同时满足状态页账号匹配和多个独立公网目标验证通过。
5. **恢复 UU**：网络确认后检查 UU 用户态进程和外部连接。用户态假死时只清退用户态并按自启命令启动；用户态完全退出时直接启动；两种情况都必须再次确认进程和外部连接，失败则进入冷却后的再次尝试并明确告警。
6. **结束状态**：只有网络验证和 UU 本机外连均通过才显示“在线”；验证码、凭据、Portal 改版、UU 启动失败和服务器拒绝必须显示独立原因。

“重新断开再登录”是故障确认后的受控兜底步骤，不是每次检测都执行。无条件断开会主动制造 UU 中断，并可能触发校园网账号的设备数淘汰。

## 3. 故障分类与动作

| 故障 | 判定证据 | 自动动作 | 禁止行为 |
| --- | --- | --- | --- |
| Wi‑Fi 断开/无 IPv4 | 接口状态、地址、受限探测 | DHCP 续租或 `netsh wlan connect` | 网络未恢复时重启 UU |
| Wi‑Fi 已连接但 Portal 失效 | Portal 状态页要求认证 | 复用会话尝试 Portal 登录 | 盲目反复提交凭据 |
| Portal 要验证码 | 登录页存在同源验证码字段和图片 | OCR，最多有限次数，失败后冷却重试 | 猜测验证码、跨源取图 |
| 公网假死 | 闸门 + 至少两个交叉目标失败 | 保留接口，按阶段重连/重新认证 | 只依据 Windows Wi‑Fi 图标判在线 |
| 账号被服务器挤下线或旧会话假死 | Wi‑Fi/IPv4 仍在，Portal 要求认证，或 Portal 显示本账号在线但公网闸门与至少两个交叉目标连续失败 | 普通认证后仍为 `AUTHENTICATED_DEGRADED` 时，在两轮接口绑定失败、身份匹配和用户开关允许后，仅重建本机无线会话；然后强制重新登录 | 未确认账号/IP/MAC、探测不可信、每次探测失败都注销、注销账号的其他设备 |
| UU 用户态假死 | 网络真实可用，但 UU 用户态无外部连接 | 重启用户态并验证进程/外连 | 清退 `GameViewerService`、`Server`、`Healthd` |
| UU 用户态完全退出 | 网络真实可用，用户态缺失，可找到自启命令 | 启动 UU 并验证 | 把服务存活当作 UU 在线 |
| 监测器自身崩溃 | 进程不存在 | 由 Windows 独立自启/恢复机制拉起 | 依赖进程内线程自救 |

## 4. 状态机

`HEALTHY` → `NETWORK_DEGRADED` → `WIFI_RECOVERING` → `PORTAL_AUTHENTICATING` → `INTERNET_VERIFYING` → `UU_VERIFYING` → `HEALTHY`

失败分支进入 `WAIT_RETRY`，记录失败原因并按冷却时间复试。验证码、账号密码错误、Portal 结构变化分别显示，不把它们合并成笼统的“网络断开”。

## 5. 安全和并发边界

- 密码只从 Windows 凭据存储读取；日志不得出现密码、验证码、Cookie 或完整登录响应。
- 单一恢复执行器串行化 Wi‑Fi、Portal、代理和 UU 操作，禁止多个恢复线程同时提交认证。
- 认证前先读取状态页；已是本账号在线时先复用会话。若其后仍确认公网不可用，才进入受限的本机旧会话恢复，不把 Portal 在线单独视为网络恢复。
- 活动 Wi‑Fi 的旧会话重建要求恢复开关处于开启状态。普通认证明确返回 `AUTHENTICATED_DEGRADED`，两轮绑定该 Wi‑Fi 的探测均要求闸门失败且至少两个交叉目标失败，随后核对 Portal 账号、当前 IP 与同一设备记录中的 MAC。每 6 小时最多一次，预约先落盘；账号/IP/MAC 不一致、快照或探测不可信、取消、冷却中均保留现有会话。
- 同一网络世代和冷却窗口内不重复清退/启动 UU。
- UU 恢复只操作用户态进程；系统服务需要管理员权限时不得隐式操作。

## 6. 验收标准

### A. 正常断链恢复

断开 SNNU Wi‑Fi 或制造 Portal 失效，恢复后：日志依次出现网络恢复、认证成功、公网验证成功；最终状态为 `online`。

### A-2. 五设备上限导致的被挤下线

保持本机 Wi‑Fi 关联和 IPv4，使用第 6 台设备触发服务器挤出本机；助手必须在连续探测失败后把状态标为假死/需认证，重新提交本机账号、密码和 `mobile`，通过状态页账号匹配和公网交叉验证，随后确认 UU 用户态外连恢复。若 Portal 仍显示本账号在线但公网不可用，显式开启无线会话重建后，才可在两轮本机 Wi‑Fi 多目标失败与账号/IP/MAC 一致时下线本机并重新认证。若服务器再次挤出本机，日志必须显示服务器侧认证失败或再次掉线原因，不得显示“在线”。

### B. 图形验证码

使用真实四位数字验证码页面：同一会话取图、提交移动运营商和账号密码，成功后状态页账号匹配。OCR 失败时不得提交猜测，并在有限重试后给出明确待处理状态。

### C. UU 假死

保持网络真实可用，使 UU 用户态无外部连接：助手清退用户态、按自启命令启动，确认用户态进程回来并重新建立外部连接；服务进程不被清退。

### D. UU 完全退出

用户态进程不存在但自启项存在：助手能够启动并验证；无启动命令时明确报告“无法自动启动”，不能报告成功。

### E. 长时间无人值守

验证登录后自启、睡眠/休眠保护、监测器崩溃后的独立恢复机制。电脑断电、系统死机、未登录 Windows、Portal 改版和 UU 控制端不可用属于不可保证场景，必须在 UI/文档中明确标注。

## 7. 剩余风险与修复边界

| 风险 | 能否修复 | 当前处理 | 后续验收 |
| --- | --- | --- | --- |
| Wi‑Fi 已连接但公网假死 | 可以部分自动修复 | 多目标接口绑定验证；普通认证后仍降级时，在用户开关开启且本机身份核对通过后，最多每 6 小时重建一次本机无线会话 | 需在真实 Portal 上验收登录、验证码、公网与 UU 外连；外部服务拒绝或验证码不能识别时不能保证自动恢复 |
| 四位图形验证码变化或 OCR 失败 | 只能部分自动化 | 同会话取图、格式校验、刷新后有限重试；失败不猜测 | 真机验证码成功/失败各一次，失败必须停在“需要处理” |
| 校园账号并发设备限制（实测最多 5 台） | 服务器规则无法由客户端消除 | 已在线时不重复 POST；检测被挤下线后按冷却重新认证，避免无故提交把其他设备挤掉 | 5 台以内保持本机在线；第 6 台触发后记录服务器实际挤出与恢复结果 |
| UU 用户态假死或完全退出 | 可以恢复本机进程 | 只操作用户态，验证进程和外部 TCP，失败后再次进入恢复门 | 网络恢复后模拟用户态无外连和完全退出 |
| UU 控制端/服务端拒绝或会话失效 | 不能由本机单独保证 | UI 只报告本机进程与外连证据 | 需要 UU 服务端会话或官方 API 的端到端确认 |
| 监测器自身崩溃 | 可以修复 | v0.11.0 增加独立 Windows 任务计划守护、心跳过期检测和有界自动拉起 | 杀掉监测器进程后由任务计划拉起并恢复监测 |
| 电脑断电、Windows 死机、未登录用户 | 不能由进程内逻辑保证 | 文档和 UI 明确标记为不可保证 | 采用 BIOS/UPS/Windows 登录策略另行保障 |

## 8. 当前版本对照

- v0.11.3：新安装或配置缺少无线会话重建选项时默认开启，升级保留已保存的布尔值。会话重建的本机身份核验、探测与冷却条件沿用 v0.11.1。

- v0.11.2 修复：延迟出现的四位验证码沿用配置的同会话有限重试；电脑重启前先完成最后一轮 Portal/公网恢复并拒绝在验证码、凭据或已认证降级状态下重启；更新提示准确区分线上版本和本机版本。

- v0.11.0 新增：约 60 秒恢复预算（30 秒连续失败确认、首次认证立即执行、失败后 5 分钟冷却）、同会话三次验证码挑战和多路图像预处理一致性判断、用户态 UU 自动恢复新安装默认开启、独立 Windows 任务计划守护（15 秒心跳、45 秒失联判定、10 分钟内最多拉起 3 次）。
- v0.11.1 修复：Portal 仍显示本账号在线但公网持续失败时，普通认证后的 `AUTHENTICATED_DEGRADED` 结果可以进入活动 Wi‑Fi 本机旧会话重建；每次下线前两轮执行 Wi‑Fi 接口绑定多目标验证，并继续校验 Portal 账号、IP、MAC、取消状态和 6 小时持久化冷却。沿用 V0.11 同会话验证码登录和网络恢复后 UU 外连验证。该能力受现有 `standby_session_reset_enabled` 明确开关控制，升级不隐式启用。
- v0.10.5 已具备并继续保留：Wi‑Fi/IPv4/公网多目标验证、Portal 移动运营商参数、凭据读取、恢复后 UU 用户态重启、UU 外部 TCP 验证、用户态缺失探测修复、中文 Windows 电源计划解析，以及 UU 启动后未外连时的再次恢复门。
- 仍需现场验收：真实校园网验证码、5 台上限触发的被挤下线、真实断链、守护任务在目标电脑上的注册/拉起，以及 UU 控制端会话可用性。
- 外部限制：校园网账号最多 5 台只是当前实测值，服务器仍可能提前清理会话或改变策略；助手不能强制保持超过服务器上限的设备，也不能保证 UU 控制端实际远控会话，本机只能提供进程和外连证据。
