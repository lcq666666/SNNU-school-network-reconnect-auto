分支：`fix/observer-degraded-20261112`（基线 `759f6328` = v0.7.0 源码 + 1 个文档提交）。
阶段定位：修复「长断连自锁」的**放大器**，不是全部修复；后续阶段见 §7。

## 1. 问题复述与证据

2026-11-12 15:50、16:20 两次约 10 分钟断连（10 分 00 秒 / 9 分 55 秒），日志全天
171 次 `SNAPSHOT_UNTRUSTED`、8 次 `COLLECT_FAIL`、29 次 `DNS_FAILURE`，断连期间
**没有任何 Portal 重连动作**，直到网络侧自愈 `NETWORK_UP` 才标记恢复。

外部诱因是 DNS / Clash 分流抖动（WLAN 物理 Up、以太网 Disconnected、公网探测报 `dns`
失败且「直连不通但代理通」）；但把一次可恢复的抖动放大成 10 分钟不可用，是软件自身的
fail-closed 自锁：

```
三轴采集失败/超时 → 无新快照发布 → 旧快照 STALE → observe(trusted=False)
  → TrayFailoverBridge 换 RefusingExecutor（Portal/Wi-Fi/Metric 全拒绝且不消耗冷却）
  → campus_failover.tick(trusted=False) 连状态机都不推进
  → campus_dual_path.tick() 立即返回
```

**量化根因（仓库内已有，非本次推测）**：`docs/P8真实环境验收手册_2026-10-15.md`
§「2026-10-16 观测层（P7.5-1A）"三轴采集超时"根因量化诊断」

| 量 | 值 |
|---|---|
| 单轴探测最坏预算 | 27.0 s（网关 2 + TCP 2 + HTTP 3 + DNS 2，各 3 s 超时，串行） |
| 两轴最坏 | 54.0 s |
| **真机实测一次完整三轴 evaluate** | **21.1 / 22.0 s（中位 21.6 s）**；另一次 46 s |
| 旧采集预算 `snapshot_timeout` | **12 s** |
| 旧有效期 `snapshot_max_age` | **8 s** |
| 工作线程节拍 `interval` | 15 s |

⇒ 21.6 s > 12 s，**每轮必然超时**；且 8 s < 21.6 + 3 s，**即便侥幸在预算内完成，
快照也会在下一个节拍前过期**。P8 受控实验 `(8,12,3)` 得 `timeouts=6 / collect=0 /
trusted=False（永远）`，`(45,45,3)` 得 `timeouts=0 / collect=1 / trusted=True`，
与生产日志 100% 吻合。

## 2. 方案选择

P8 给出三档：A（只改预算，规格内立即可用）、B（改 P1 探测层短路/并发，治本但面大）、
C（先 A 再评估 B，推荐）。**本阶段实施 A**，与「一次只做一个阶段」的推进约定一致，
且 A 是唯一不需要改动探测语义、可完全离线回归的一档。

关键约束（P8 已核实，避免重复踩坑）：`_read_snapshot_keys` 对 `snapshot_max_age`
限幅 **[1, 30]**、`snapshot_timeout` 限幅 **[3, 60]**，被
`tests/unit/test_v03_p75_1a_supplement.py` 钉为规格 ⇒ 早先口头提的 `max_age=45` 越界不可用。
故规格内可用组合为 **`max_age=30` / `timeout=45` / `interval=3`**。

### 3.1 为什么必须加「旧配置迁移」

`load_config()` 用 `cfg.update(_read_snapshot_keys(text))`，即**直接读原始 JSON**。
旧版会把 `(8, 12, 3)` 写进 `tray_config.json`；只改 `DEFAULT_CONFIG` 对已存在
的配置文件**完全无效**，重新打包后用户仍会卡在自锁。因此 `_read_snapshot_keys`
在限幅后做精确匹配迁移：仅当 `(max_age, timeout) == (8, 12)` 时升级到 `(30, 45)`，
`interval` 原样保留；任何其他组合视为用户显式配置，**不静默改写**。

### 3.2 `check_snapshot_budget()` 固化的三条不变量（纯函数、零 I/O）

1. `collect_timeout >= measured_collect` —— 否则每轮必然超时；
2. `max_age >= measured_collect + min_interval` —— 否则慢采集必然产生 STALE 空窗；
3. `max_age >= min_interval` —— 否则每轮必有不可信空窗。

注意比较基准是**实测**采集耗时而非 `collect_timeout`：规格允许 `max_age <= 30` 而
`timeout` 可达 60，`max_age >= timeout` 不可能作为不变量。

## 4. 安全契约（不变）

**fail-closed 语义一字未改**。本阶段只放宽「多久算新鲜」和「允许采集跑多久」，
没有删除或绕过任何闸门。以下仍一律 `trusted=False`、`RefusingExecutor` 仍
`attempted=False / executed=False`（不消耗冷却、零网络副作用）：

- 快照结构不完整（`light_snapshot` 缺 `recommendation`/`generated_at`）；
- 代次失效（配置 / SSID / DHCP / 接口身份变化）；
- 真实过期（age > max_age）；
- 采集抛错、采集超时；
- 接口约束失败（`PROBE_UNRELIABLE`，V0.5 契约，本阶段未触碰）。

## 6. 残余风险（明确留给后续阶段）

1. **`max_age(30) < collect_timeout(45)`**：病态采集跑满 timeout 时仍会出现
   最多一拍 `STALE`（P8 亦注明「节拍边界余量极薄」）。本阶段不消除，由阶段 B
   的**有界降级**（`DEGRADED` 模式 + last-known-good 有限宽限）处理。
2. **采集持续失败仍会自锁**：断网时 `netdiag` 的 `adapters`/`default_routes`
   报 `RuntimeError`，无新快照发布 ⇒ 旧快照在 30 s 后过期 ⇒ 重新进入零副作用。
   预算放宽只解决「慢采集必然超时」，**不解决「采集失败」**。这是 15:50 / 16:20
   两次长断连的另一半根因，必须由阶段 B/C 的降级执行器解决。
3. **最坏 54 s 采集仍超 45 s 预算**：P8 方案 B（每轴 TCP/HTTP/DNS 首个成功即
   短路或并发）尚未实施，建议作为独立阶段评估。
4. **配置层隐患未处理**：Portal 认证冷却 60 s 低于下限 180 s、`AutoAdminLogon`
   未配置、以太网物理断开导致双链路实际只剩一条 —— 均属 L0 运行环境，不在代码补丁内。
5. **必须重新打包 exe 才生效**：改的是源码，运行中的 `CampusReconnect.exe`
   （v0.6.10）不受影响；发布需走 release 工作流并做 sha256 校验。

## 7. 后续阶段（按序，逐阶段验收 + 推送）

- **阶段 B**：`ObservationResult` 增加 `FULL / DEGRADED / REFUSED`，`stale_for`
  与 last-known-good 快照，超 45–60 s 进入有限宽限；结构不完整 / 代次失效仍严格 fail-closed。
- **阶段 C**：分级执行器。`DEGRADED` 只放行 Portal 认证 + Wi-Fi 重连白名单，
  仍拒绝 `METRIC_WRITE` / Clash 配置改写 / UU 重启；每 epoch 限次 + ≥180 s 冷却。
- **阶段 D**：公网探测加 IP 直连通道，把 DNS 抖动判为 `DNS_DEGRADED` 而非
  `NETWORK_DOWN`（对应日志里「直连不通但代理通：结论矛盾，探测不可信」）。
- **方案 B（可选）**：压缩 P1 探测开销，消除 54 s 最坏预算。
