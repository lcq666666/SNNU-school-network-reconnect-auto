## 1. 四块改动

### 块 1：双轴探测 + Clash 假死自愈

- **新模块** `campus_clash_health.py`：`ProxyAxisResult` / `ClashHealth` / `ClashHealPlan`；
  `classify`（直连通 + 代理 timeout/connection = Clash 假死；dns / http_status / mismatch / 未知 = unknown；
  双不通 = offline）、`probe_via_proxy`（注入会话，不自建真实会话）、`check_endpoint`
  （Clash 端点 TCP 检查，默认 `127.0.0.1:7897`）、`heal_plan`（attempts 0 → 关开一次系统代理，
  1 → 重启 Clash Verge Rev 进程，≥2 → 空计划并建议人工）、限幅 `clamp_interval` 5..120（默认 5）、
  `clamp_threshold` 1..10（默认 2）、`clamp_cooldown` 60..3600（默认 60）。
- **接线**（`campus_reconnect_tray.py`）：`_verify_online_async` 在直连验证后调用
  `_dual_axis_clash_check(direct_ok)` 补测代理轴；假死时按计划自愈
  （`_clash_heal_execute`，注入点 `_clash_heal_ops` 供测试替换；真实执行只在 Windows 上：
  toggle = 关开系统代理，restart_verge = `taskkill /f /im "Clash Verge.exe"` 后尝试拉起）。
- **默认值**：`campus_core.Config` 与托盘 `DEFAULT_CONFIG` 的 interval 15→5、threshold 3→2、
  cooldown 180→60（配置仍可改，限幅兜底；`TimerTable` 默认值 15/3/180 未动，低层计时器多处测试依赖，改动风险大）。
- **测试**：`tests/unit/test_v06_clash_health.py`（49 个）+ 集成测试（`test_v06_integration.py` 内 3 个）。

### 块 2：有线转 Wi-Fi（自启链）

- **新模块** `campus_wifi_bringup.py`：`WifiAdapterState` / `BringupStep` / `BringupPlan` / `BringupResult`；
  `plan`（顺序 enable_adapter → radio_on → ensure_profile → connect → wait_ip；已连目标 SSID 返回空步骤）、
  `build_snnu_open_profile_xml`（开放式 profile：authentication=open、encryption=none、SSID 做 XML 转义并附 hex）、
  `run_bringup`（经注入 ops 执行，任一步失败即停，疑似权限不足时明确写“需要管理员权限”）、
  `is_stable_for_failback`（连续成功 ≥5 且持续 ≥120s 才切回有线）。
- **接线**：首次启动 5 秒后弹一次确认（`_prompt_auto_switch_once`，纯函数
  `should_prompt_auto_switch` / `apply_auto_switch_consent`：只在“从未问过 + 仍是 MONITOR + 未授权”时弹一次；
  同意 → `failover_mode=AUTO` + `auto_switch_authorized=true` 并保存；拒绝 → 保持 MONITOR 但记已问过，不再弹）；
  `repair_once` 在调 `repair_service` 前若 Wi-Fi 未连目标 SSID 则先跑 `_wifi_bringup`
  （Windows 上执行自启链，profile XML 先写临时文件再 `add profile`；非 Windows 返回 None，走旧的 `wifi_reconnect`）。
- **配置**：新增 `v06_auto_prompted: False`、`clash_heal_enabled: True`、`uu_escalation_enabled: True`
  （`_read_v06_keys`，非法值回退默认）。
- **测试**：`tests/unit/test_v06_wifi_bringup.py`（35 个）+ 集成测试（确认函数、非 Windows 返回 None）。

### 块 3：UU 后台重启两档

- **新模块** `campus_uu_recovery.py`：`decide`（六条全部成立才重启：有断网事件、恢复前 UU 在运行、
  验证通过、开关开启、冷却通过、同 epoch 未重启过；任一否决返回 False 并给中文 reason）、
  `tier1_processes()` = (GameViewer.exe, GameViewerLauncher.exe)、
  `tier2_processes()` = Tier1 + (GameViewerServer.exe, GameViewerHealthd.exe)、
  `GameViewerService` 永远不在清退范围、`should_escalate`（60 秒是宽限期：59 秒继续等不升级，
  满 60 秒仍未确认回来才升级；硬失败不立即升级（托盘按 V0.4 行为只提示、不额外清退））、
  `confirm_back`（进程全回来且直连验证通过才 True）、`diagnose_snapshot`
  （按进程分组，只取 pid/name/local/remote/state 白名单字段，空输入返回 `["UU 进程未发现"]`）、
  `clamp_uu_cooldown`（60..3600，默认 300）。
- **接线**：`_uu_recovery_after_verification` 在原有 `schedules_uu_restart` 门后加 `uu_decide` 门禁
  （断网段开始时 `_probe_tick` 达到失败阈值调用 `_note_outage_for_uu`，只读探测 UU 是否在运行，
  记诊断行；事件消费后清 `_v06_had_outage`）；Tier1 后若未确认回来，60 秒定时器
  （`_schedule_uu_tier2_check`，经 `uu_should_escalate` 判定）再确认一次，仍未回来升 Tier2
  （`_uu_tier2_restart`，同一事件的升级，不另计一次、不重置冷却）。
  Tier1 失败（重启命令本身失败）时**不**立即升 Tier2：按 V0.4 行为如实提示、不改状态、不额外清退——
  重启命令已失败时再杀 Server/Healthd 只会让 UU 更死，升级只走 60 秒超时确认。
  一次恢复事件最多重启一次。
- **集成时发现并修复的 bug**：`_uu_tier2_restart` 原先用 `_norm(p.name)`（去 `.exe`，如 `gameviewer`）
  去比带 `.exe` 的小写清单（`gameviewer.exe`），永远匹配不到，Tier2 是空操作；
  已改为两侧都用 `_norm` 归一，集成测试 `test_uu_tier2_restart_kills_tier2_and_confirms_back` 证实
  三进程（101/102/103）均被清退并按自启项重启。另删了一个未被调用的重复升级方法
  `_uu_confirm_and_escalate`（超时升级已有定时器；硬失败按 V0.4 行为处理，不另设升级路径）。
- **测试**：`tests/unit/test_v06_uu_recovery.py`（35 个）+ 集成测试（门禁三态、Tier2 清退、超时语义、定时器升级）。

### 块 4：界面 CustomTkinter 深色重做

- **接线**（`campus_reconnect_tray.py` 内，原地改，不换网页版）：`_open_dashboard` 先试
  CustomTkinter（`_open_dashboard_ctk`），失败回退原 ttk 代码（原 ttk 代码不动）；

## 8. V0.6.1 A+D+E 融合仪表盘（2026-11-11，用户敲定）

用户在 5 个组件方案里选了 **A 单页大状态 + D 时间线主导 + E 仪表大屏**三者结合：
既简单清晰，又能看到日志/历史时间线，还要有仪表大屏。只改托盘仪表盘相关代码，
网络核心逻辑（探测/切换/UU 重启）一律不动；版本号仍 0.6.0。

### 布局（上 → 下）

1. **顶部 A 大状态区**：状态灯 ●（30 号字）+ 大字状态词（30 号粗体，只写中文状态词，
   如“网络正常/离线/恢复中”）+ 一句结论 headline；恢复中/降级时灯呼吸闪烁（沿用 pulse 逻辑），
   健康时常亮。
2. **中部 E 三环仪表**：以太网、SNNU Wi-Fi、UU 远程各一个 Canvas 手绘圆环（110×110，

## 9. V0.6.2 自动更新提醒（2026-11-11，用户要求：装好 exe 后不是死的）

本地用户从 Release 装好 exe 后，远端 GitHub 一发新 Release，app 要在用户
本地提醒有更新可用。**只提醒，不下载、不静默安装、不自动重启**——下载与
安装永远由用户在浏览器里自己点。

### 检查时机

- 启动后 60 秒做第一次检查（等网络稳定，不抢启动流程），之后每 6 小时一次。
- 检查挂在已有网络工作循环上（`_worker_loop` 每轮调 `_maybe_check_update`），
  不另起常驻线程；检查本身走独立短命线程（`campus-update`），不阻塞探测循环。
- 设置页“诊断”里有“立即检查更新”按钮，跳过定时马上查一次（开关关闭时也可用）。
- 设置里有 `update_check_enabled` 开关（默认 True），关掉后不再自动检查。

### 提醒方式（三处同时有）

1. **仪表盘顶部横幅**：有新版本时在仪表盘顶部出现琥珀色横幅
   “发现新版本 vX.Y.Z（当前 v0.6.0）— 只提醒，不自动下载安装”，
   带“下载更新”按钮（打开浏览器到该 Release 页面）和“以后再说”按钮。
2. **托盘气泡通知**：查到新版本时弹一次气泡“发现新版本 vX.Y.Z”。
3. **设置页“更新”区**（诊断页底部）：显示“当前版本：v0.6.0 · 最新版本：vX.Y.Z
   （有更新可用）”，以及自动检查开关与“立即检查更新”按钮。

### 去重规则（气泡与横幅分开记，原因不同）

- **气泡只弹一次**：`update_notified_tag` 记在配置里，同一版本第二次检查到
  不再弹气泡；下次启动若仍是该版本，也不重复弹。
- **横幅一直留着，直到用户处理**：`update_dismissed_tag` 记在配置里，只有用户
  点了“以后再说”或“下载更新”后横幅才不再出现；没点过时重启后横幅还会出现
  （因为用户还没处理，不是重复骚扰）。设置页则始终显示最新版本，不受去重影响。

### 检查失败时

没网、GitHub 超时、非 200、JSON 异常、缺 `tag_name`、tag 无法解析——全部静默：
只写一条 `[更新] 检查失败：<原因>` 日志，不弹窗、不报错、不影响主流程，
下次到点再查。

### 实现

- 新纯逻辑模块 `campus_update.py`：`parse_version`（`"v0.6.0"`/`"0.6.0"`，
  非法返回 None）、`is_newer`（语义版本比较，任一无法解析返回 False）、
  `check_latest(session, repo)`（GET

## 10. V0.6.1 Windows CI 修复（2026-11-11）

背景：`v0.6.0` 标签（1617d91）触发的 release #2 与 ci #73 都失败，
Windows CI 上 pytest 均为 **9 failed、1149 passed、1 skipped**；
同一提交在 Linux 全量上是 1151 通过、7 失败、1 跳过，失败集合不同。

未推送（按本次任务约定，push 由主代理做），共 8 个提交。

### 逐项根因 + 修法 + 证据

**第 1 项 `test_env_smoke.py::test_ruff_cli_available`——测试查错了位置，不是依赖缺失。**
根因：测试只查 `sys.executable` 所在目录。Linux / venv 里脚本就在解释器旁边，
但 GitHub `setup-python` 的 Windows 安装把 `python.exe` 放 `…\x64\`、
脚本放 `…\x64\Scripts\`，只查前者永远找不到。证据：`requirements-lock.txt`
有 `ruff==0.14.14`（第 38 行），`requirements-dev.txt` 与 `pyproject.toml`
也有；同一任务里 `python -m ruff check .` 那步通过了（否则 pytest 根本不会跑），
说明模块装着呢；测试文件、工作流、ruff 锁定版本自 V0.5 基线（0e71c73）起
一字未动。修法：用 `sysconfig.get_path("scripts")` 查 pip 真正的脚本安装目录，
原目录留作兜底；没动依赖清单与工作流。

**第 2 项 `test_i2_01_offline_closed_loop_recovery_within_one_interval`——两层原因叠加。**
(a) V0.6 回归：托盘 V0.6 新增 4 处等待（Clash 自愈 1s/2s、Wi-Fi 等 IP 2s、
UU Tier2 确认 10s），直接走模块级 `time.sleep`；V0.6 之前托盘里没有任何等待调用，
只有 `campus_remote_app._SLEEP` 是导入时抓取的。计时器测试装上虚拟时钟后，
残留的后台线程恰好在此时调用它，虚拟时间被多推进几秒，探测时刻从
`[0, 15, 30, 45]` 漂到 `[0, 15, 30, 50]`（CI 上是 49.0）。证据：单独复现脚本
3 次全过、全量 Linux 基线也过，说明不是测试本身的容差问题，是 V0.6 引入的
真实回归向量。修法：托盘导入时抓一份真实 sleep（`_REAL_SLEEP = time.sleep`），
4 处等待全改走它；Tier2 测试改打 `tray._REAL_SLEEP` 的桩。
(b) V0.5 引入的竞态：后台三轴采集在独立线程里调 `internet_ok`，会偷吃
计时器测试记录型假件的条目，探测时刻表多一条 0.0。修法：计时器测试助手
（`test_v03_p2_timer_separation.py` 与 `test_v03_p0_timer_forensics.py`
的 `_make_app`）把 `_snapshot_collector` 桩成返回 `None`（快照不可信，
fail-closed，不影响计时器断言）。新增回归测试
`test_v061_tier2_sleep_does_not_advance_virtual_clock` 与
`test_v061_tray_has_no_patchable_sleep_calls`（托盘源码里不得再出现
可被虚拟时钟替换的等待调用）。

**第 3 项 `test_v04_launch_detached_splits_quoted_and_unquoted_commands`——两个叠加的 bug。**
(a) `os.path.isdir(directory)` 把关：CI 上 `C:\_study\GameViewer` 不存在就传了
`cwd=None`；(b) `os.path.sep in exe` 判断：Linux 上反斜杠路径永远进不去分支。
修法：按两种分隔符（`\` 与 `/`）取目录，不依赖本机 `os.path.sep`，不要求目录
真实存在；目录真不存在时 Popen 报错、由已有 except 转成 `(False, 说明)`，
不静默用错误目录启动。真机上 GameViewer 目录存在，行为不变。
证据：本文件 31 个测试在 Linux 上全过（修前此用例失败）。

**第 4–9 项（V0.4 校验 / UU 重启 6 个测试）——V0.6 把 Clash 检查同步插进了校验线程。**
根因：V0.6 在 `_verify_online_async` 的线程里、UU 重启与失败提示之前，
同步调了 `_dual_axis_clash_check(ok)`。代理轴每站 3 秒超时（最多约 9 秒），
自愈还要拉 `taskkill` 再等 2 秒；校验通过后的 UU 重启与失败提示都被它拖后，
Windows CI 上测试的 3 秒 `wait_until` 上限内收不到结果。Linux 上回环拒绝是
瞬时的，所以本地全过。已排除另外两个嫌疑：V0.6.1 融合仪表盘（这些测试根本
不打开仪表盘）与 V0.6.2 更新检查钩子（只在 `_worker_loop` 里跑，这些测试
不用它）——对照 V0.5 基线的 diff 也证实校验路径里 V0.6 只加了这两处与
`_note_outage_for_uu`（阈值路径）。修法：(a) 新增 `_start_clash_check_async`，

(b) V0.4 测试助手关掉 Clash 轴（`clash_heal_enabled=False`）：轴本身由
`test_v06_clash_health.py` 的 49 个测试覆盖；且不关的话，CI 上自愈会真的
改跑步机的系统代理（指到 127.0.0.1:7897），可能连累同任务后边的
`gh release upload`；(c) 同两个助手把 `_snapshot_collector` 桩成返回 `None`：

就不断，第二次校验永远不触发（复现：V0.5 基线单跑此用例 5 次里也失败 1 次；
修前本分支单跑 5 次全失败，修后 5 次全过）。

**附带 bug `tools/build_release.py`——Windows 控制台 cp1252 下中文输出报 `UnicodeEncodeError`。**
根因：构建脚本打印中文失败信息（“测试 / 静态检查未通过……”）时，
`print` 在 cp1252 控制台上直接抛错，构建日志被异常截断。修法：`main()` 开篇
