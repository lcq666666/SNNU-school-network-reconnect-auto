## 引言

这次发现的是一个比校园网自动认证更重要的问题：真正需要的已经不只是"校园网自动重连软件"，而是一套保障远程电脑持续联网的双网络故障切换系统。

需求可以明确为：有线网络正常时，电脑优先使用以太网；有线网络不可用时，即使网线还插着，也能自动切换到 SNNU Wi-Fi，必要时自动完成校园网认证；有线网络恢复稳定后，再安全切回有线网络。整个过程不能出现两个网络互相抢占、反复认证或频繁切换的问题。

这个目标可以实现，但需要修改现有程序的网络决策方式，而不只是增加几条断网检测规则。

## 一、检查现有代码后的结论

重新读取 GitHub 分支 `fix/reconnect-stability-20261013`（当前 HEAD：`4900ca95`）后，结论是：现有程序能够判断"电脑能不能访问公网"，却没有充分判断"电脑应该通过哪张网卡访问公网"。

| 现有行为                                     | 双网卡下的问题                      |
| ---------------------------------------- | ---------------------------- |
| `internet_ok()` 使用全局网络路径进行 HTTP 探测       | 检测不到有线、无线各自的独立健康状况           |
| `watch()` 连续 3 次检测失败后尝试修复                | 可能把有线网络故障错误地交给 Wi-Fi 认证模块处理  |
| `repair_service()` 检查 SNNU、解析 Portal 并认证 | 并不负责决定 Windows 的流量应该走有线还是无线  |
| `wifi_reconnect()` 可以重新连接无线              | Wi-Fi 连上不意味着 Windows 已切换默认路由 |
| 托盘程序显示"在线 / 重连中 / 离线"                    | 没有明确区分"以太网在线"和"Wi-Fi 备用在线"   |

另外，Windows 选择路由时，会综合接口 Metric 和路由 Metric；自动 Metric 通常还会参考网卡速率，所以有线网络经常获得更高优先级。即使某个有线接口已经无法访问公网，Windows 也不一定马上放弃它（参考 Microsoft Learn）。

因此建议：保留 V0.2 已经完成的校园网认证引擎，新增一个独立的"双网卡智能调度层"，把"检测、选择、切换、认证、恢复"分开管理。

# CampusReconnect V0.3 — 双网卡智能故障切换与远程在线保障开发方案

**开发基础**：`lcq666666/SNNU-school-network-reconnect-auto`

**基线分支**：`fix/reconnect-stability-20261013`

**基线提交**：`4900ca95a670e47b31f36bb41cc4815b4cc0aa2c`

**开发原则**：保留 V0.2 认证能力；新增网络智能调度；远程连接安全优先；先完成离线测试与本机前台验证，再启用真实路由切换。

## 1. 需求与目标

### 1.1 网络使用场景

Windows 电脑同时具备：

- Ethernet：插入网线的有线网络，作为首选网络。
- Wi-Fi：陕西师范大学 `SNNU` 校园无线网络，作为备用网络。
- Clash Verge Rev：系统代理已开启，TUN 关闭。
- 远程桌面软件：用户需要从外部远程访问该电脑。

必须支持两张网卡同时存在、以太网物理连接正常但公网不可用、SNNU 已连接但尚未认证、两个网络都中断以及有线网络恢复等情况。

### 1.2 核心行为

**场景 A：有线网络正常**

- 电脑优先使用有线网络。
- SNNU 可以保持无线关联，作为备用。
- 后台正常检测网络，但不发送重复校园网认证请求。
- 不修改 Clash 代理状态，不频繁改变路由。
- 不影响现有远程连接。

**场景 B：网线连接着，但有线网络无法访问公网**

- 检测有线网络的真实连通性。
- 确认故障不是单个网站、DNS 或探测服务器造成的误判。
- 检查 SNNU Wi-Fi 是否已连接。
- 如未连接，尝试无线重新关联并等待获取 IP。
- 检查 SNNU 是否可以正常访问公网。
- 如果需要 Portal 认证，则通过 SNNU 网卡执行自动认证。
- 确认 Wi-Fi 可用后，将默认公网流量切换到 Wi-Fi。
- 保持以太网网卡启用，继续观察其恢复情况。

**场景 C：Wi-Fi 已接管，后来有线网络恢复**

- 独立检测有线网络，而不是仅观察当前默认公网访问。
- 连续确认有线网络稳定。
- 满足恢复时间、切换冷却时间等条件后，才将有线网络重新设为首选。
- 如果切换后远程链路异常，执行安全回退。
- 不主动注销 SNNU，不强制断开 Wi-Fi。

**场景 D：两个网络同时不可用**

- 有限频率地尝试网络恢复。
- 不在两张网卡之间无限来回切换。
- 不重复提交错误账号或无效认证请求。
- 保留最新故障原因和恢复尝试记录。
- 任意一条网络恢复后，重新进入正常监控状态。

### 1.3 成功标准

在至少一条物理网络和对应上游服务可用的前提下，程序能够自动发现、选择和恢复可用的公网路径。

需要特别区分：

- 网络恢复：电脑可以访问公网。
- 远程恢复：远程控制客户端能够重新建立会话。

网络恢复不代表原有 TCP 连接一定无缝保持。应将远程客户端的自动重连能力纳入最终验收。

## 2. 系统架构调整

建议新增一层 `NetworkFailoverManager`，而不是将有线网络逻辑直接塞入 `repair_service()`。

新结构：

1. **NetworkObserver**：收集有线、无线接口和路由信息。
2. **InterfaceHealthChecker**：分别测试 Ethernet 与 SNNU 的连通性。
3. **NetworkFailoverManager**：决定当前应该使用哪条网络。
4. **RouteController**：负责经过授权的路由优先级调整、验证与回退。
5. **SNNUAuthService**：沿用已有 `campus_core.repair_service`，仅在需要时执行校园网认证。
6. **RemoteSafetyGuard**：保护远程控制相关的网络状态，并处理异常回滚。
7. **TrayUI**：展示当前主链路、备用链路、故障、认证和切换状态。

关键原则：

**路由调度不负责登录，校园网认证不负责选择主网卡。**

这两个模块通过明确的请求与结果对象交互，避免相互触发造成循环。

## 3. 网卡识别与独立健康检测

### 3.1 建立网卡清单

使用 Windows 网络接口 API 或 PowerShell NetTCPIP 相关接口，读取：

- 网卡名称、接口索引、适配器标识。
- 物理与无线网卡类型。
- 网卡启用状态和连接状态。
- IPv4、IPv6 地址。
- 默认网关、DNS。
- 默认路由。
- 自动 Metric、接口 Metric、路由 Metric。
- 当前 Wi-Fi SSID 和配置 Profile。
- 当前访问公网实际选择的网络路径。

优先使用稳定的网卡标识持久化配置，不依赖网卡显示名称的完全一致性。

排除 Clash、VPN、Hyper-V、WSL 等虚拟网卡的自动优先级修改；但在诊断时保留它们的路由信息。

### 3.2 独立网络检测

必须实现三个互不混淆的检测结果：

- `ETHERNET_HEALTH`：有线网络是否真正可用。
- `WIFI_HEALTH`：SNNU 无线网络是否真正可用。
- `SYSTEM_HEALTH`：Windows 当前默认网络是否可用。

禁止仅靠 `requests.Session(trust_env=False)` 判断流量经过哪张网卡。该参数只能帮助绕过代理环境配置，不能指定 Windows 出口网卡。

每张网卡的探测应明确指定网络接口或源地址，并确认实际路由。Windows 环境中需采用支持接口绑定的传输实现；如果只绑定源地址却无法证明实际出口，判定为 `UNKNOWN`，而不是假定成功。

对每个接口采用多点检测：

- 第一层：网卡是否连接、是否存在可用 IP 和网关。
- 第二层：能否通过该接口访问外部 IP 或建立 TCP 连接。
- 第三层：HTTP/HTTPS 内容完整性验证。
- 第四层：DNS 是否正常。
- 可选第五层：远程控制服务所需的网络是否可达。

不能仅依赖 ICMP Ping，也不能因为某一个检测站点失败就判定整个互联网断线。

### 3.3 结果分类

至少区分：

- `HEALTHY`：路径可用。
- `LINK_DOWN`：物理连接或无线关联中断。
- `NO_IP`：没有有效地址。
- `GATEWAY_UNREACHABLE`：网关不可达。
- `DNS_FAILURE`：DNS 故障。
- `CAPTIVE_PORTAL`：需要认证。
- `INTERNET_UNREACHABLE`：网关正常，但公网不可达。
- `PROBE_UNRELIABLE`：探测结果不可信。
- `UNKNOWN`：无法可靠判断。

任何 `UNKNOWN` 或单探测失败，均不能直接触发破坏性网卡操作。

## 4. 网络优先级与自动切换

### 4.1 默认有线优先

当两条网络都可用时，让 Ethernet 具有更低的有效路由开销。

例如初始配置可采用：

- Ethernet：InterfaceMetric = 10。
- Wi-Fi：InterfaceMetric = 50。

这只是建议值。必须结合现有默认路由、RouteMetric、VPN 及 IPv6 情况检查，不可单纯认为设置接口 Metric 就一定改变目标路径。

如果 Windows 原有路由优先级已经正确，且故障切换测试可以通过，则优先保留原配置。

### 4.2 故障时 Wi-Fi 接管

切换应分两个阶段。

**阶段 A：准备备用路径**

1. 确认 Ethernet 连续检测异常。
2. 检查 SNNU 是否关联成功。
3. 必要时重新连接 Wi-Fi。
4. 等待无线 IP、网关就绪。
5. 使用无线接口专属连接检测 SNNU 状态。
6. 如有 Portal 认证需求，通过 SNNU 接口完成认证。
7. 验证备用路径具有公网访问能力。

**阶段 B：正式切换**

1. 保存当前真实路由和网络配置快照。
2. 重新确认有线故障仍然存在、无线仍然可用。
3. 对相关接口或默认路由调整 Metric，让 Wi-Fi 成为优先出口。
4. 验证 Windows 实际选择的出口接口已改变。
5. 验证公网与远程服务连接。
6. 标记 `WIFI_BACKUP_ACTIVE`。
7. 记录切换原因、耗时与结果。

建议先使用可逆的路由优先级调整，不通过禁用 Ethernet 强行实现切换。

对于 IPv6 也必须检查有效默认路由。不能只切 IPv4，导致应用仍然通过不可用的有线 IPv6 路由出网。

### 4.3 有线网络自动恢复

Wi-Fi 接管后，必须继续对 Ethernet 进行独立探测。

建议初始条件：

- Ethernet 连续稳定至少 120 秒。
- 满足至少 5 次独立成功探测。
- 距离上一次实际切换至少 300 秒。
- 当前没有进行中的 Portal 认证。
- 当前没有其他路由变更任务。
- 如果检测到敏感远程会话，允许推迟自动切回。

满足条件后才能尝试恢复有线优先。

若切回之后发现链路不稳定，应撤销本次切换，并再次进入恢复观察期，禁止短时间内反复切换。

## 5. 全局状态机

网络调度与校园认证应使用独立状态。

主要状态：

- `ETHERNET_PRIMARY`：有线主用，网络正常。
- `ETHERNET_SUSPECT`：有线疑似异常，等待进一步确认。
- `WIFI_PREPARING`：准备无线备用链路。
- `WIFI_AUTHENTICATING`：SNNU 需要认证，正在执行。
- `WIFI_SWITCHING`：执行经过批准的路由切换。
- `WIFI_BACKUP_ACTIVE`：Wi-Fi 已接管。
- `ETHERNET_RECOVERY_CHECK`：正在检查有线恢复稳定性。
- `ETHERNET_FAILBACK`：准备安全切回有线。
- `BOTH_OFFLINE`：两条路径均不可用。
- `MANUAL_REQUIRED`：凭据、Portal 或系统权限等问题需要人工处理。
- `PAUSED`：用户暂停自动调度。

状态转换须有明确前置条件、超时、冷却、失败处理和日志。

禁止一轮检测同时触发：

- Wi-Fi 重新连接；
- SNNU Portal 登录；
- Ethernet Metric 修改；
- Clash 系统代理修改。

所有可能影响网络连接的动作应由单一调度器串行安排。

## 6. 防止网络冲突与认证风暴

### 6.1 有线正常时禁止自动重登 SNNU

这是最重要的规则。

只要确认当前 Ethernet 正常承载公网流量，普通后台检测不得触发 SNNU Portal POST。

Wi-Fi 可以保持关联，用于备用状态监测，但不应因一次无线探测失败就反复重新认证。

### 6.2 所有 SNNU 请求必须限定接口

当 Ethernet 和 SNNU 同时在线时，Portal IP 可能通过非预期接口访问。

需要确保：

- Portal 端口解析经过 SNNU。
- Portal 状态读取经过 SNNU。
- Portal 认证请求经过 SNNU。
- 认证成功后的验证经过 SNNU。

对于无法可靠约束出口接口的情况，不发送真实凭据，返回"无线认证路径未确认"。

### 6.3 增加切换与认证冷却

路由切换和 Portal 认证使用独立计时器。

建议：

- 网络检测间隔：5–15 秒，可配置。
- 主链路故障：连续 3 次可靠失败才触发。
- Portal 重试冷却：至少 180 秒，失败后适度退避。
- 链路切换最短间隔：300 秒。
- 已确认的凭据错误：停止后台自动登录。
- Portal 结构未知：停止自动认证，等待人工处理。

不允许通过反复调整 Metric 试探网络是否已经恢复。

## 7. 远程连接安全保护

### 7.1 禁止默认执行的危险操作

自动模式默认不得：

- 禁用当前可用的网络适配器。
- 对网卡执行重置。
- 删除全部默认路由。
- 清空 DNS 配置。
- 重启 Windows 网络服务。
- 断开所有连接来测试网络切换。
- 强制关闭或重启远程控制软件。
- 修改 Clash 的 TUN 或代理配置。

### 7.2 路由变更需要事务和回滚

每次切换前保存：

- 目标网卡标识。
- 原始接口 Metric 和自动 Metric 状态。
- 原始默认路由及 RouteMetric。
- IPv4/IPv6 相关配置。
- 当前主路径。
- 变更的唯一操作编号。

先执行条件校验，再应用最小变更，随后检查结果。

应有独立于主监控线程的本机恢复机制，以防主程序在路由切换途中崩溃。

回滚不能简单地"永远恢复到有线优先"：若有线确实不可用，应优先保留已验证可用的 Wi-Fi 路径。只有确认变更异常或需要恢复安全快照时，才按预定义策略回退。

### 7.3 远程会话的现实限制

默认路由切换可能导致远程 TCP 会话重新建立。应用必须明确提示：目标是自动恢复联网和远程可重连，而不是保证现有远程会话完全不丢包。

建议单独检测所使用的远程控制客户端是否正常运行，以及其必要服务是否可达。

同时确认：

- Windows 不会在长期无人值守时自动睡眠。
- 远控软件能随系统启动。
- 远控软件允许无人值守访问。
- 远控软件发生断线后可以自动重连。
- Windows 重启后的登录、凭据和自动运行机制经过验证。

## 8. Windows 平台特殊处理

### 8.1 同时保持有线与无线

检查 Windows Connection Manager 的连接策略，以及网卡驱动的有线/无线自动切换功能。

如果系统策略会在 Ethernet 在线时强制断开 WLAN，就无法实现真正的 Wi-Fi 热备用。

须支持检测这种情况，并给用户清晰提示。只有经过本机验证与授权，才调整相关系统策略。

### 8.2 权限分离

普通的网络探测和校园认证不应要求管理员权限。

网络路由与 Metric 修改可能需要提升权限，因此将写操作集中到单独的 Windows 适配层。

优先采用：

- 普通权限执行监测与认证。
- 单独授权受限的路由控制任务。
- 路由控制任务仅允许修改用户明确配置的物理网卡。
- 遇到权限缺失时提示，而不是持续失败重试。

不要把整个托盘程序默认提升到管理员权限。

### 8.3 路由和网络变化事件

除定时探测外，增加对 Windows 网络变化事件的观察：

- 网卡连接状态变化。
- IP 地址变化。
- 默认网关变化。
- 默认路由变化。
- Wi-Fi 连接与断开。
- 系统从休眠或待机恢复。

事件用于提前触发检测，不直接触发危险切换动作。

## 9. Clash Verge 兼容性

现阶段用户仅开启系统代理，TUN 关闭。

V0.3 的核心链路管理应该独立于 Clash 工作。

- 有线健康时，不修改代理。
- Wi-Fi 接管时，不修改代理。
- 有线恢复时，不修改代理。
- 仅当此前获得用户明确授权，并且本地 Clash 代理端口实际可用时，才保留已有的代理恢复功能。
- SNNU Portal 地址继续采用 Direct/Bypass 策略。

建议在托盘设置里提供一个单独的"网络切换期间保持 Clash 原样"选项，作为默认值。

## 11. 托盘界面需求

用户不应该再只看到"在线"两个字。

推荐展示：

- 当前主网络：Ethernet / SNNU。
- 当前备用网络：SNNU / Ethernet。
- 有线状态：正常 / 异常 / 恢复检测中。
- Wi-Fi 状态：已连接 / 需要认证 / 已认证 / 不可用。
- 当前系统出口：显示实际路由选择。
- 远程保障：启用 / 已暂停 / 需要人工处理。
- 最近一次切换时间、原因和结果。

提供三种模式：

1. **智能自动**：有线优先，失败切 Wi-Fi，稳定后切回。
2. **仅监测**：观察双网络状态，不修改系统路由。
3. **手动锁定**：锁定 Ethernet 或 Wi-Fi 优先，仍显示健康告警。

手动锁定不应自动禁用另一张网卡。

## 12. 分阶段开发计划

### P0：诊断与风险确认

不修改真实路由，不提交 Portal 认证。

完成：

- 确认两张物理网卡标识。
- 读取真实默认路由和 Metric。
- 检查是否允许有线与无线同时连接。
- 确认 SNNU 能否保持无线关联。
- 确认主用路径与远控所需路径。
- 完成有线与无线独立探测设计。

出口条件：能够准确区分当前有线和无线健康状态。

### P1：双网络只读监测

只开发观察和状态机，不启用实际切换。

完成：

- 物理网卡发现。
- 每接口连通性探测。
- 默认路由识别。
- 网络状态分类。
- 托盘显示当前主备关系。
- 日志说明"如果允许切换，将选择哪条路径"。

出口条件：有线故障时不会误认 SNNU 故障，不会执行多余认证。

### P2：SNNU 备用链路准备

完成：

- Wi-Fi 关联检查与自动连接。
- SNNU Portal 识别。
- 无线接口专属 HTTP 访问与认证。
- 认证后的无线链路独立验证。
- 禁止使用 Ethernet 出口提交 SNNU 凭据。

出口条件：能够在双网卡同时连接时可靠验证 Wi-Fi 的可用性。

### P3：自动路由切换

完成：

- Ethernet → SNNU。
- SNNU → Ethernet。
- 路由快照。
- 路由验证。
- 异常回滚。
- 滞回与冷却。
- 单一网络操作调度。

出口条件：有线故障能够自动切换，且恢复后不会频繁抖动。

### P4：远程保障

完成：

- 远程控制软件连通性检查。
- 远程会话敏感期的安全切回策略。
- 后台监控崩溃恢复。
- Windows 启动及恢复运行验证。
- Wi-Fi、路由、Portal 与远程控制日志关联。

出口条件：远程访问能够在实际故障切换后重新建立。

### P5：正式验收

只有通过双网卡真机测试后，才将 V0.3 设置为默认自动模式。

未经验证前，保留 V0.2 版本及其可恢复安装方式，不直接覆盖稳定版本。

## 13. 验收测试矩阵

| 场景              | 预期结果                       |
| --------------- | -------------------------- |
| 有线、Wi-Fi 都正常    | 优先有线；Wi-Fi 不重复认证           |
| 有线网线拔出          | Wi-Fi 自动接管                 |
| 有线物理连接仍在，但公网中断  | 能识别逻辑断网并切 Wi-Fi            |
| Ethernet DNS 故障 | 正确识别和处理，不把它误认为 Portal 凭据错误 |
| Wi-Fi 已连接但未认证   | 仅通过 SNNU 进行认证              |
| Wi-Fi 认证失败      | 不无限重试，不擅自修改其他连接            |
| 两个网络都不可用        | 不反复改变 Metric               |
| Wi-Fi 已接管，有线恢复  | 稳定观察后切回                    |
| 有线公网间歇性抖动       | 不持续来回切换                    |
| 同时运行 CLI 和托盘    | 单实例保护生效                    |
| 路由修改时程序异常退出     | 可恢复到安全的已知路由状态              |
| 系统睡眠后恢复         | 自动重新检查路径                   |
| Windows 重启      | 已配置的监控按预期启动                |
| 远程控制正在连接时主链路故障  | 备用路径恢复，远控能够重新连接            |
| 用户暂停自动调度        | 不发生自动认证或路由修改               |
| Clash 系统代理开启    | Portal 可直连，代理不被意外关闭        |

所有有副作用的测试必须在离线 Mock 通过后，才允许于本机受控执行。

## 14. 发布条件

V0.3 的发布必须满足：

- 不退化 V0.2 的 SNNU 认证能力。
- 普通在线状态没有重复认证。
- 有线健康时默认使用有线。
- 有线失效时能识别 Wi-Fi 作为备用路径。


- 能处理"网线插着但公网不通"。
- 能验证实际流量出口已经切换。
- 有线恢复后具有防抖切回机制。
- 路由修改具备最小权限、快照与安全回退。
- 不擅自关闭远控软件、Clash 或其他网卡。
- 通过全部离线测试和至少一次受控真实故障切换。
- 通过真实远程重连测试后，才将自动切换设置为长期无人值守默认模式。

**禁止将单纯"脚本成功修改 Metric"作为验收通过。真正的验收是可用公网路径恢复，以及远程访问可重新建立。**

# 附：对 V0.2 现有代码的额外修复建议

以下两点是在阅读 V0.2 代码后发现的，对远程使用尤其重要。

## 附 1. 当前冷却机制可能暂停网络检测

在 `campus_reconnect.py` 的 `watch()` 中，重连失败后会设置 `next_attempt`，随后可能直接休眠直到冷却结束。托盘版的 `_next_probe_time()` 也存在类似逻辑。

这意味着：原本只是为了限制 Portal 认证次数的 180 秒冷却，也可能导致公网探测被暂停。

V0.3 应彻底分离三个计时器：

- 网络检测计时器：持续运行。
- Portal 认证冷却：只限制认证。
- 网卡切换冷却：只限制路由变更。

即使处于认证冷却期，网络健康检测也不能停止。

## 附 2. 必须检查 Windows 是否禁止有线、无线同时保持连接

微软的 Windows Connection Manager 支持多种策略，有的策略会在以太网在线时限制 WLAN 自动连接，甚至阻止手动连接（参考 Microsoft Learn）。

所以开发前必须先确认本机能否真正保持两张网卡同时连接。否则程序的备用链路设计可能被 Windows 或网卡驱动策略抵消。

# 附：最终应该选择哪种备用模式？

推荐：**Wi-Fi 热备用模式**——有线与 Wi-Fi 同时保持可用，Windows 优先走有线。软件独立检测备用网络，在允许且必要的情况下维持 SNNU 的认证状态，以缩短故障接管时间。

前提：学校允许双连接，且本机能够可靠地按网卡发送认证请求。

备选：**Wi-Fi 温备用模式**——有线正常时只让 SNN



U 保持关联，不主动维持认证；出现故障后才完成无线认证及路由切换。更保守、对校园认证系统干扰更少，但切换通常更慢。

对于长期无人值守、随时可以远程控制电脑的目标，倾向于最终采用热备用模式，但先从温备用模式开展受控测试。

# 结语

双网卡自动切换可以显著提高可用性，却不能绝对保证远程连接永不中断。即便两条网络都健康，切换也可能改变出口 IP，造成现有远程会话短暂断开。因此远控软件本身还需要具备断线自动重连能力。

最终建议：将 V0.3 定位为"智能双网络故障切换"，保持 V0.2 稳定认证引擎不变，按照 P0 → P5 逐步实现。先完成双网卡独立检测，再引入认证与路由控制，最后以真实远程故障测试验收。这是目前最符合使用场景、也最能避免把远程电脑意外弄失联的方案。
