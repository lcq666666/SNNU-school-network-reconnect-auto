### 1.2 三种启动形态（按验收项选用）

| 形态 | 命令 | 用途 | 是否占单实例互斥体 |
|---|---|---|---|
| 一次性命令 | `status` / `once` / `snnu` / `route` / `remote` / `netcheck` / `failover` | 自检、单次、A 组主力 | 仅 `once`、`snnu --auth`、`route --apply/--auto` 占 |

| 托盘（图形） | `campus_reconnect_tray.py`（或 `run_tray.bat`） | 人工看状态/模式/气泡 | **占**（与 watch 互斥） |

> **互斥体规则**（务必记住，否则命令会互相拦）：`watch` / `once` / `snnu --auth` /

> `remote` / `snnu`（不带 `--auth`）/ `route`（只读快照）**不占**，可与托盘并存。
> 做只读项时不必退托盘；做 `watch`/`once` 前**先退托盘**。

托盘三种模式（配置在 `tray_config.json`）：
- `MONITOR`（**默认**）：仅监测，不做任何真实动作；
- `AUTO`：智能自动切换（**需显式授权**，出厂 `auto_switch_authorized = False`）；
- `LOCKED`：手动锁定优先出口，仍做健康告警、零执行。

### P8-1 双网卡同时连接及实际出口识别

**目的**：证明软件能同时区分 Ethernet / Wi-Fi / System 三轴健康，并正确识别系统实际出口。

**命令**

```

**预期（PASS）**

- `WIFI_HEALTH` 反映 SNNU 无线轴真实状态；Wi-Fi 轴探测**不沿用系统最佳路由**；
- `SYSTEM_HEALTH.egress.if_index` 指向 Windows 当前真实出口；
- `recommendation.preferred = ethernet`、`would_switch = false`。

**本次实测（2026-10-15 晚；修复 F75-09/F75-10/F75-11 后复跑）**
- 以太网：`HEALTHY`，`egress_confirmed=true`，源地址 `192.168.124.9`（ifIndex=10）✅
- 无线：`INTERNET_UNREACHABLE`，`egress_confirmed=true`，源地址 `10.138.241.249`（ifIndex=5）⚠️
  证据：网关 `10.138.0.1:443` 无响应但 `:80` 可达、DNS 可解析、`captive.apple.com` HTTPS 报 `SSLError`
  → 典型"已关联、未认证"的 Portal 形态。
- 系统轴：`online=false` ⚠️（**两层原因，均已取证**）
  1. 修复前恒为 `探测来源: system_probe 抛错`——这是 F75-11 把异常吞成"假离线"，已修复；
  2. 修复后是**诚实结果**：默认探测目标在本校园网不可用——
     `www.msftconnecttest.com` **始终 DNS 解析失败**（`errno 11001`），
     `captive.apple.com` **偶尔首次请求不匹配**；实测 6 次独立会话 **5/6 报在线**
     （证据 `snapshots/p8-1_default_probe_flakiness.log`）。
- 决策：`preferred=ethernet`、`would_switch=false` ✅

**结论：`PARTIAL`** — 出口识别、三轴分离、优先路径判定**全部正确**；两处与"理想预期"不一致，均登记在案：
1. 无线轴状态是 `INTERNET_UNREACHABLE` 而非 `CAPTIVE_PORTAL`。原因：该校园 AP 对未认证客户端的
   公网 HTTP 直接丢包（`ConnectionError`）而非重定向到登录页，健康分类器拿不到"Portal 重定向"证据。
   **"需要认证"的权威判定在 `snnu` 命令（P8-2）**，不依赖此轴（见 §7.2 K-1）。
2. `SYSTEM_HEALTH.online=false` 属**探测目标环境性误判**：校园网封锁 `8.8.8.8`/`1.1.1.1:443`
   与 `msftconnecttest`（已用 `Test-NetConnection` 实测：`8.8.8.8:443=False`、`1.1.1.1:443=False`，
   而 `www.baidu.com:443=True`、`www.apple.com:443=True`、`202.117.144.205:80=True`）。
   **实际公网可用**（代理 `127.0.0.1:7897` 已开，浏览正常）。判读时**以各业务轴 + 实测为准**（见 §7.3 K-2）。

### P8-2 SNNU 备用链路可达性

**目的**：证明能**独立地**经 SNNU 网卡解析 Portal 端口并判断是否需要认证，且**无法证明出口时不发凭据**。

**命令**

```

**预期（PASS）**
- 报告 Wi-Fi 关联状态、无线源地址、Portal 首页/端口解析**来源**；
- Portal 分类为 `CAPTIVE_PORTAL`（需认证）或已在线；**不提交任何凭据**；
- 若出口无法可靠约束，返回"无线认证路径未确认"并 fail-closed（也算 PASS）。

**首轮实测（2026-10-15 晚）：触发阻断性缺陷 F75-09 → `FAIL`**
- 输出：`结论: 未成功（E_SNNU_NO_IP）`，`说明: SNNU 已关联但无有效 IPv4：无法限定出口，不发送凭据`；

  实测：`ipv4_ready('WLAN')=False` 而 `ipv4_ready(None)=True`。离线测试的假数据缺这个空行，故全量回归全绿也漏检。
  → 已修复（F75-09，提交 `6b1cf62`）。

**修复后复跑（同日）**：`结论: 成功`，`阶段: DONE`，`ok=true`
```json
"detail": "SNNU 已关联但需要 Portal 认证（只读识别，未提交凭据）",
"link":   {"ssid":"SNNU","state":"ASSOCIATED","if_index":5,
           "source_ip":"10.138.241.249","has_ipv4":true},
"binding":{"ok":true},
"egress": {"proof":"CONFIRMED","egress_if_index":5,
           "detail":"IP_UNICAST_IF 回读 + 源地址约束"},
"portal": {"port":8609,"source":"根页面 JS 跳转","status":"AUTH_REQUIRED"},
"credentials_sent": false
```
- ✅ 关联状态 / 无线源地址 / `IPv4 就绪=True`（F75-09 已修）；
- ✅ **出口证明 `CONFIRMED`**：`IP_UNICAST_IF` 回读 + 源地址约束（证明 Portal 请求确实经 SNNU 网卡）；
- ✅ **动态端口解析有效**：首轮解析出 `8601`，复跑解析出 `8609`（不写死端口）；
- ✅ **Portal 状态判定为 `AUTH_REQUIRED`**（需认证）；该结论依赖本轮修复的 **F75-10**——

## 7. 已知问题与本次真机发现

### 7.1 F75-09（已修复 ✅）— `ipconfig` 分块解析导致 SNNU 链路误判"无 IP"
- **现象**：`snnu` 恒返回 `E_SNNU_NO_IP`，即使 WLAN 已有 `10.138.241.249`。
- **根因**：真机 `ipconfig` 在适配器名与属性之间有**空行**，`parse_ipconfig_ipv4` 按空行切块后，
  含接口名的块不含 IPv4 行 → 指定接口时恒 `False`。
- **影响**：`snnu` 只读/`--auth`、`wifi_reconnect` 的"等待 IP 就绪"。
- **修复**（提交 `6b1cf62`）：`parse_ipconfig_ipv4` 改为"逐行扫描 + 记住最近的适配器标题行"，新增
  `_ADAPTER_HEADER`（匹配中英文适配器标题）；补 3 条**按真实 ipconfig 布局（适配器名后带空行）**
  的回归用例。真机复验：`ipv4_ready('WLAN')` 由 `False` → `True`；P8-2 由 `FAIL` → `PASS`。

### 7.2 K-1（待评估）— 无线轴无法区分"需认证"与"不可达"
- 本校园 AP 对未认证客户端直接丢包（`ConnectionError`），健康分类器拿不到 Portal 重定向证据，
  故无线轴恒为 `INTERNET_UNREACHABLE`。后果：AUTO 状态下 ethernet 故障时走 `BOTH_OFFLINE`
  （仅限频重连、不自动 Portal 认证）。**"需要认证"的权威判定在 `snnu` 命令**。
- 待定：是否需要为"无线轴疑似 Portal"增加保守判据（例如网关仅 :80 可达 + TLS 拦截
  + DNS 可解析 → 提示疑似 Portal）。**先记录，不在本阶段擅自改动。**

### 7.3 K-2（环境性 + 已修根因）— 系统轴 `online=false`
- **表象**：系统轴恒报离线，修复 F75-11 前还会显示 `探测来源: system_probe 抛错`。
- **两层根因**：
  1. **代码缺陷 F75-11（已修复 ✅）**：接口绑定污染了 urllib3 的进程级全局 pool 映射，
     使随后所有普通 HTTP 探测抛 `AttributeError`，被 `evaluate` 的 `except Exception` 吞成"抛错 → 离线"；
  2. **环境性**：默认探测目标在本校园网不可用——`msftconnecttest` 恒 DNS 失败、
     `captive.apple.com` 偶发首次失配（6 次实测 5/6 在线）。
- **判读**：以各业务轴 + 实测为准；如需消除 2，可按 README §10 调整 `DEFAULT_PROBES`（**属配置变更，待授权**）。

### 7.4 K-3（无人值守缺口，来自 `remote` 自检）
- 睡眠超时未关闭、`AutoAdminLogon` 未配置、外部崩溃恢复机制需人工配置、远控自动重连需人工确认。

### 7.5 F75-10（已修复 ✅）— 只读状态页把"跳转到登录页"当作不可解析
- **现象**：`snnu` 只读识别恒报 `Portal 状态：未识别`，即使链路确实需要认证。
- **根因（真机实测）**：未认证的 SNNU 链路上 `userstatus.jsp` 返回 **302 → `login.jsp`**；
  `read_status_page` 只接受 2xx，把该 3xx 当作"无法解析"返回 `None`。
- **影响**：P8-2 的"Portal 分类"判据无法达成；只读模式失去"需要认证"的权威信号。
- **修复**（提交 `d93c23b`）：对**同源且落在 Portal 流程内**（`login.jsp`/`userstatus.jsp`）的
  301/302/303 直接判 `AUTH_REQUIRED`；非同源/流程外仍返回 `None`（fail-closed，不臆断）；
  **不跟随跳转、不发送任何凭据**。复验：`[Portal 状态] AUTH_REQUIRED`。
  > 注：`run()` 在 `--auth` 时直接进入 `_authenticate`，**不依赖**本状态，故此项不阻断 P8-4。

### 7.6 F75-11（已修复 ✅）— 接口绑定污染 urllib3 全局 pool 映射（**最隐蔽**）
- **现象**：`netcheck`/`failover` 的系统轴恒为 `探测来源: system_probe 抛错` + 离线；
  `watch` 反复出现假"连续 3 次失败，判定疑似掉线"(K-4)。
- **根因**：`campus_transport._ScopedPoolManager.__init__` 就地修改 `pool_classes_by_scheme`，
  而该 dict 是 **urllib3 模块级共享对象**（`PoolManager.__init__` 直接把它挂到实例上）。
  因此**只要发生过一次接口绑定**，同进程内所有普通 `HTTPAdapter` 都会建出受限 pool；
  它们缺少 `transport`，于是抛 `AttributeError`（**非 `RequestException`**），
  逃过 `probe_online` 的异常处理，最终被 `evaluate` 的 `except Exception` 吞成"抛错/离线"。
- **最小复现**：绑定前后，全局 pool 类由 `HTTPConnectionPool` → `_ScopedPool`；
  普通 `GET` 由 `HTTP 200` → `AttributeError: 'NoneType' object has no attribute '_connect_socket'`。
- **修复**（提交 `f36ad5e`）：改为给实例一份 `pool_classes_by_scheme` 副本；
  两个受限连接在缺 `transport` 时按 fail-closed 抛 `NewConnectionError`（不再 `AttributeError`）。
  补 3 条隔离回归用例。复验：绑定后普通 `GET` 仍 `HTTP 200`，系统轴不再报"抛错"。

### 7.7 K-4（待处理）— 探测目标导致的"假掉线"告警
- 现象：P8-3 的 25 分钟窗口内出现 **10 次** `连续 3 次失败，判定疑似掉线`，紧接
  `重连结果: 未成功（公网已连通，无需认证）`；**未实际认证**，故不危害"零重复认证"结论。
- 根因：`DEFAULT_PROBES` 在本校园网不可靠（见 K-2 第 2 条），叠加已修复的 F75-11 放大效应。
- 待办（**需授权**）：是否按 README §10 调整 `DEFAULT_PROBES` / 降级 §7.7 告警阈值；
  或为"疑似掉线但探测自愈"增加抑制窗口。**先记录，不擅自改动。**
