## 2. 验收标准逐条核对

### 2.1 F04：四类故障均有清晰结果；验证前 `ProxyEnable` 未被修改（T08/T09）
- 命令：`.venv/Scripts/python.exe -m pytest tests/unit/test_proxy_controller.py tests/unit/test_f04_proxy.py -q`
- 覆盖：查询拒绝（`deny_query`）、句柄打开拒绝（`deny_open`）、写入拒绝（`deny_set`）、
  写入中途失败、**回滚成功**、**回滚失败**、刷新失败、写入后快照读取失败。
- 断言要点：
  - 任一失败路径下 `ProxyEnable` 均保持原值（无部分写入）；
  - 句柄恒以 `KEY_QUERY_VALUE | KEY_SET_VALUE` 打开（先读后写）；
  - `ProxyApplyResult.rollback_ok` / `refresh_ok` **分别**报告，回滚失败时 detail 明示
    “回滚失败，系统代理可能处于中间状态”；
  - 刷新失败时 `ok=False`，不谎报完全成功。
- **结论：通过 ✅**

### 2.2 F05：网络恢复与代理联动是两项独立结果；默认不启用、不猜测端点（T10）
- 覆盖场景：端点未监听、非本机地址（`8.8.8.8:1080`）、缺失端点、多协议历史值、
  既有 `ProxyOverride` / `AutoConfigURL`（PAC）保留、停用只改 `ProxyEnable`、幂等无变更。
- 断言要点：
  - `enabled=True` 且无用户确认端点 ⇒ `E_PROXY_ENDPOINT_INVALID` 且不写注册表；
  - 既有绕过列表与 PAC 在启用/停用时保持不变；
  - 托盘层：代理联动失败时 `state["mode"]` 仍为 `online`，通知文案如实说明
    “网络已恢复，但系统代理未开启”。
- **结论：通过 ✅**

### 2.3 F03：T05/T06/T07 转绿；字符串开关/bool 充当 int/未知版本不启用代理、不杀死线程
- 命令：`.venv/Scripts/python.exe -m pytest tests/unit/test_f03_config.py -q`
- 覆盖：未知键隔离（且**原始值不入日志**）、`interval="bad"`、bool 充当 int、
  负数/小数/超大值、`clash_auto_proxy="false"`、`browser_fallback="false"`、
  JSON null/list/截断/损坏、未知 `schema_version`。
- 断言要点：非法输入一律回退安全默认值；`clash_auto_proxy` 恒为 `None/True/False`；
  配置错误只产生可见告警，监测线程不受影响。
- **结论：通过 ✅**

### 2.4 F13：写拒绝/磁盘失败/JSON 截断/并发保存下旧文件完整、失败不显示成功（T25/T37）
- 覆盖：`Path.write_text` 抛 `OSError`（旧文件保持原样且返回 `False`）、
  数据目录不可写（父路径是文件）、并发 5 线程保存（最终文件仍是合法 JSON、
  无临时文件残留）、成功保存后可读回且未知键不落盘、只读日志目录降级为仅控制台输出。
- **结论：通过 ✅**

### 2.5 F01：最多一个认证任务在途、最多一个网络线程；任务中改配置不影响本次请求（T01/T02/T03）
- 覆盖：

- **结论：通过 ✅**

### 2.6 F02：mock 端口解析/凭据/结果处理抛错，线程不静默失效、UI 可见、后续命令仍可处理（T04）

  工作线程意外退出 ⇒ `worker_status()` 报“监测已停止”，`restart_monitor()` 可恢复。
- **结论：通过 ✅**

### 2.7 F10：pause/quit 在等待/授权/POST 阶段注入，不启动后续 POST/Edge/代理写入（T21）

  认证过程中暂停 ⇒ 不打开 Edge、不写系统代理，结果标注“已取消”；
  退出后 `repair_once` 立即拒绝且工作线程在超时内退出（有界 join）。
- **结论：通过 ✅**

### 2.8 F11：首跑/第二凭据写入失败/读取异常/更新中断均覆盖，不删除用户既有记录（T22/T34）

  恢复失败 ⇒ 明示“恢复原凭据失败”；原本无记录 ⇒ 仅清理本次写入的账号；
  清除 ⇒ 只删本程序记录；`service` 名与引擎常量一致。
- **结论：通过 ✅**

## 6. 与计划的偏差与说明

1. **提交拆分**：计划建议 4 个 `fix:` 提交（代理 / 配置 / 排他 / 取消）。
   实际拆为 **2 个提交**：`feat: add windows adapters...`（适配层 + 结果契约 + 适配器测试）
   与 `fix: validate config, persist atomically, serialize repairs, add cancellation`。
   原因：`campus_reconnect_tray.py` 为一次性整体重构（工作线程、命令队列、取消令牌、
   授权版本、代理事务、配置持久化互相耦合），无法在不产生不可运行中间态的前提下按
   文件切分；适配层已单独成提交，职责边界仍然清晰。
2. **F05 的端点来源**：本阶段实现「必须由调用方显式给出端点」+ 本机白名单 + TCP 监听探测。
   设置面板新增「代理端点 host:port」输入项；`CLASH_SERVER_DEFAULT` 仅作为首次询问弹窗中
   的**建议值**展示，不再被硬编码写入注册表。
3. **`--force` 与暂停规则**：暂停状态下手动重连默认不启动；用户主动点击「立即重连」时
   经确认后才允许一次（`_repair_override`），不影响 `paused` 配置本身。
4. **未触碰阶段 3 范围**：`repair_once` 仍保留 `cfg.get("yys") or "mobile"` 与现有
   `portal_login` 判定逻辑，因此 F06 / F09 / F15 的回归用例按计划继续失败。
5. **打包配置**：`campus_reconnect.py` / `campus_reconnect_tray.py` 现依赖同目录新增模块
   `campus_core.py` / `campus_windows.py`。PyInstaller 从入口脚本自动分析同目录导入，
   但**需在阶段 4（F22）构建验证时确认**新模块被打入产物。
